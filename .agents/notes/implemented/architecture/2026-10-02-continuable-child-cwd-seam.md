# Agent Note: Provider-chosen working directory for a continuable child

Status: implemented

English | [中文](2026-10-02-continuable-child-cwd-seam.zh.md)

## Problem

A continuable child could not be given a working directory of its own. `childSessionMeta` in `packages/subagent/subagent/src/child-agent.ts` wrote `cwd: parentHeader.cwd` unconditionally, so every child Session inherited its delegating parent's cwd, and `withContinuableReturnGuidance` in `packages/subagent/subagent/src/continuation-messages.ts` appended a sentence that was only true in that case — "The parent shares your workspace but does not automatically receive your transcript, tool output, or reasoning." A provider's whole participation in a continuable child was `prepareContinuable`, and the `ContinuableCreateSpec` it returned carried only the optional parent-history seed.

The use that forced the question is the experimental Projects and Threads feature: a Project Session delegates to background Threads, and each Thread is meant to run in its own `git worktree` on its own branch, so parallel children never share a checkout. The harness already holds the mechanism this needs. `SandboxPolicyService.resolve` computes `workspaceRoot: resolveWorkspaceRoot(session?.header.cwd ?? this.workspaceRoot)` (`packages/sandbox/sandbox-policy/src/index.ts`), so a Session's header cwd **is** its write boundary. Handing a child Session a worktree path as its cwd confines that child's writes to the worktree, with no new sandbox mode, no new process boundary, and no new enforcement mechanism. What was missing was a way for a provider to say so.

The capability has to live in the subagent package rather than inside Threads because what is being generalized is not a worktree. Any continuable provider may want its child somewhere other than the parent's checkout — a build directory, a copy, a per-test fixture — and the durable half of the behaviour is a property of the continuation manager, which is the only thing that resumes a child. A provider that can only create worktrees under a package that knows about worktrees would be a feature in a seam.

## Decision

`ContinuableCreateSpec` gained `readonly cwd?: string` (`packages/subagent/subagent/src/types.ts`). Absent means the child inherits the parent's cwd, which is the default every existing provider already relies on. Present means the child is materialized there. The manager validates it before taking the child lock — `assertProviderCwd` calls `assertUsableCwd('subagent', \`provider "${provider}" cwd\`, cwd)`, the same helper the out-of-process one-shot path already used, and wraps any failure in `SubagentError(..., 'INVALID_PROVIDER_CWD')`. The value must be an absolute path to an existing directory the process can enter (`statSync().isDirectory()` plus an `X_OK` access check); a relative path, a file, and a missing directory all fail with the same code, before any child exists.

`childSessionMeta` takes a fourth argument, `overrides: ChildMetaOverrides = {}`, carrying provider-supplied `cwd` and `agentPreset` beside the three it already resolved, and it resolves `overrides.cwd ?? parentHeader.cwd` for the child's `meta.cwd`. When neither the provider nor the parent supplies one, `cwd` is omitted from the metadata exactly as before. The parent still wins nothing implicitly: a child whose parent has no cwd and whose provider names no cwd has no `cwd` key at all, not an empty string.

`SubagentContinuationManager.startContinuable` threads both values into that metadata as the child's `create.meta`, which `ctx.agents.create()` turns into the child's session header — so `header.cwd` and `header.agentPreset` are durable, and lineage, descriptor, and delegation depth travel beside them. A cold resume does not re-derive any of it: `coldResume` folds the descriptor and calls `activations.materialize` with no `create` block, which routes to `ctx.agents.resume()` and loads the persisted Session. The provider is not consulted, and the isolation survives process restart. This is the same provider-independent cold resume that [Continuable subagents](../feature/2026-07-28-continuable-subagent-conversations.md) pinned, extended from "which composition" to "which directory".

The child's initial task text follows the resolved value. `withContinuableReturnGuidance(parentId, prompt, isolatedCwd?)` now takes the child's cwd as a third argument, and the call site passes `childHeader.cwd !== parent.session.header.cwd ? childHeader.cwd : undefined` — the comparison is against the **materialized child's** header, not against what the provider claimed, so a provider that names the parent's own cwd gets the shared-workspace sentence because that sentence is then true. In the isolated case the child is told `You work in your own separate checkout at "<path>". The parent does not see files you change there until it inspects that checkout, and it does not automatically receive your transcript, tool output, or reasoning. State in the message what changed, where, and how you verified it.` The shared-workspace branch is byte-identical to the pre-change string: 405 bytes before and after, compared by running the `HEAD` revision of `withContinuableReturnGuidance` and the current one side by side (the isolated variant is 578 bytes). No snapshot in the tree carries the string. The guidance is appended only when the child's tool registry exposes `send_message`, which is unchanged.

`ContinuableCreateSpec` also gained `readonly agentPreset?: string`, letting a provider name the preset its child is composed from; absent means the child joins the parent's composed preset, the previous behaviour. It is validated by `assertProviderPreset` before materialization, which requires an `agentPresets` registry, a `presets.resolve(id)` that succeeds, and a resolved entry that is not `broken`; each failure is `SubagentError(..., 'UNKNOWN_AGENT_PRESET')`. `applyContinuableChildComposition` then mounts that preset on the child's scope when it differs from the parent's composed preset and otherwise falls back to `composeFrom`, and it takes the id from `child.session.header.agentPreset` — so a fresh creation and a cold resume compose from the same preset without the provider being involved in either decision.

A provider's coded refusal now survives the trip to a Remote caller. `providerRejection` in `packages/subagent/subagent/src/control.ts` maps any `Error` that is not a `SubagentError` and carries a string `code` to `subagent/provider-rejected` with details `{ code, message }`; `rejectPrompt` consults it before falling back to `gateway/internal`, and the helper is exported from the package index for Remote surfaces that start continuable children. A `HarnessError` subclass is the ordinary case — a worktree provider's `WorktreeError('NOT_A_GIT_REPO')` is one — and the subagent package does not enumerate provider error codes, because it does not define them. The package's own `SubagentError` codes keep their existing admission mappings; a non-`Error` throw or an error without a string `code` stays `gateway/internal`.

## What a relocated child is not confined from

This isolates writes and git state. It is not a security boundary and not isolation in general, and the seam's own documentation says so in the same terms.

- **No read fence.** A `git worktree` shares the parent repository's object store; the worktree adds its own `HEAD`, index, and refs, not its own objects. A child in a worktree can read every object the parent repository holds, including branches and reflog entries that the parent's branch-per-child policy was meant to keep separate. The sandbox vocabulary never claimed read confinement either: `SandboxMode` covers FILE effects only (`packages/sandbox/sandbox-policy/README.md`, and the [sandbox decision](../feature/2026-07-06-sandbox.md)).
- **The network is open.** Nothing in this change touches egress, and the sandbox vocabulary explicitly does not claim network or process visibility.
- **Temporary storage is not per-child.** `workspace-write` grants the backend's own temp roots alongside the workspace root, and those roots are not the worktree. The worktree default lives outside the parent checkout (`~/.dsh/worktrees` under the worktree-manager's default `worktreeRoot`), which is what makes the write confinement real, but it does nothing for a shared temp path.
- **`git push` remains possible.** The child's sandbox is the same `workspace-write` mode the parent runs in; nothing forbids a push, and a worktree is a first-class git client. Isolation here is a convention enforced by the provider's contract, not a barrier the harness installs.

## Alternatives considered

**Let the provider pass a cwd down on `ContinuableCreateRequest` instead of returning one.** The request is the manager's call into the provider; the spec is the provider's answer. A provider that learns the parent's cwd from `request.parent` (which every continuable provider already receives, in full) has no use for a copy, and a value the manager supplies could only ever be a value the manager already knows.

**Give the provider the child cwd as a capability, or let it create the Agent.** The manager calls `ctx.agents.create()` through its private activation-owner scope so that scope structurally owns every handle, which is what makes child-first teardown and the at-most-one-Activation invariant expressible. A provider that created or relocated the Agent itself would hold a handle the manager did not own, and cold resume would have to ask it for the child back — the exact coupling [Continuable subagents](../feature/2026-07-28-continuable-subagent-conversations.md) rejected when it reduced provider participation to one method. A cwd is data, and this seam takes data.

**Add a `worktree` field, or put the worktree logic in the subagent package.** The seam would then carry a git dependency and a Threads-shaped vocabulary, and a provider that wants a plain directory would be stuck with a package that cannot express it. The worktree machinery stays in `packages/subagent/worktree-manager` and `packages/subagent/subagent-thread-worktree`; the seam only accepts a path.

**Accept any string and validate it at first use.** The manager holds the earliest resolvable point, before the child lock and before `ctx.agents.create()`. Validating later would leave behind a durable Session, an Activation to roll back, and — for a worktree provider — a directory the provider now has to clean up. The tests pin the early failure by asserting that `ctx.agents.list()` still contains only the parent after a rejected cwd.

**Record the cwd in the subagent descriptor as well as the header.** The header already persists it, and cold resume reads the header for composition. A second copy would be a second fact to keep in agreement, and it would put a worktree path into a descriptor whose folding rule is otherwise provider-agnostic.

**Always send the isolated wording, or always send the shared-workspace wording.** The first would tell a child that shares its parent's checkout that it is somewhere it is not; the second would tell an isolated child that the parent can already see its files, which is the specific falsehood this change exists to stop. Branching on the materialized header keeps both texts true and leaves the default case byte-identical.

**Enumerate the provider error codes in the subagent package.** Mapping `NOT_A_GIT_REPO` to its own `subagent/` code would make this package the owner of a vocabulary it does not define, and every new provider code would become a change here. `provider-rejected` carries `{ code, message }` and leaves the routing to the caller, which is the same reason the package throws `SubagentError` for its own failures and does not re-map them.

**Add a cwd to the one-shot `SubagentStartRequest` too.** The one-shot path is the provider's: the in-process driver composes that child, and `dsh-subagent-thread-worktree` documents that its one-shot `start` shares the parent's cwd and is therefore not isolated. Nothing in the tree asks for one-shot relocation, and a service-level check on a value only a provider can honour would be a check with no consumer.

## Consequences

Any continuable provider can now place its child, and the placement is durable: the child Session's header records it, lineage and descriptor travel with it, and a cold resume restores it without asking the provider again. The value is a plain absolute path, so the same seam serves a worktree, a build directory, or a fixture.

Two new pre-existence failure modes join the set of ways a continuable start can reject without returning ids: `INVALID_PROVIDER_CWD` and `UNKNOWN_AGENT_PRESET`. Both are loud, and both are reported as the provider's fault rather than as a child-creation failure, because both are the provider's declaration being refused.

The guidance sentence is now a function of resolved state rather than a constant. A provider that returns a cwd equal to the parent's produces the unchanged text, so existing children see no difference; a provider that relocates a child gets wording that tells it to state what changed, where, and how it was verified, because the parent will not see the files.

`providerRejection` is exported, not automatic. The subagent package's own Remote surfaces are `subagent.prompt` and `subagent.interruptByParent`; `startContinuable` is not one, so a `prepareContinuable` refusal reaches a caller through the Remote surface of whatever feature started the child, and that surface must call `providerRejection` (or `rejectPrompt`) or the error still flattens into `gateway/internal`. Nothing in the tree calls it yet.

The negative guarantee is the part a reader must not get wrong: a relocated child is confined in its writes and in the git state it can change, and in nothing else. A provider that describes this to a user as isolation, or as a sandbox, is overstating it.
