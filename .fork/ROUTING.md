# Model routing — как работает сейчас

Описано 2026-10-04 по коду в этом дереве. Файл отвечает на вопрос «что происходит, когда агент делает запрос». Почему выбран именно такой вариант — в [DECISIONS.md](DECISIONS.md), на каких числах он стоит — в [MEASUREMENTS.md](MEASUREMENTS.md), что осталось сделать — в [plans/model-routing.md](plans/model-routing.md).

Маршрут называется `tiers` и живёт в трёх пакетах: `experimental/model-routing` (host), `experimental/client-ui-model-routing` (чип в композере, строка о смене модели в транскрипте и страница настроек), `experimental/model-routing-profile` (бандл, вставляющий обе строки). В профиле `web` они стоят через `link:` на это дерево, поэтому пересборка пакета видна сразу.

## Путь запроса

1. **`agent/request`.** Слушатель в `service.ts` переписывает предложение: пресет из `presetRoutes` получает `provider: tiers` и свою модель (`project` → `pro`), а Thread с tier-override получает свой тир. Уровень рассуждения при этом снимается — тир его не выбирал.
2. **Граница.** `boundaryOf` решает, можно ли вообще брать новое решение. Маршрут **не** перерешает каждый ход: смена модели или провайдера убивает prompt-кэш, а ход агента почти целиком кэшированный. Границы: `start`, `failure`, `selection-change`, `compaction`, `idle` (`cacheIdleMs`, по умолчанию 10 минут). Между ними работает пин.
3. **Решение.** Определяется тир: `fixed` (запрос назвал id из списка тира), `tier` (назвал тир) или `auto` — тогда судья решает.

   Разница между тремя случаями больше, чем кажется, и её стоит держать в голове при чтении конфигурации. Только `auto` вызывает судью. Только `auto` и `tier` ранжируют по всем моделям тира: под `fixed` кандидат ровно один (`adapter.ts`, `candidateModels`), и выбор сводится к перебору провайдеров этой одной модели. То есть «дешевейший среди избранных» работает при `auto`, а «дешевейший провайдер названной модели» — при `fixed`.
4. **Снапшоты.** Под `snapshotPolicy: latest` каждый id тира сперва резолвится в новейший снапшот своего семейства. Подробности ниже.
5. **Ранжирование.** По цене смешанной: `cached · cacheRead + fresh · prompt + output · completion`, веса по умолчанию `0.9 / 0.08 / 0.02`. Модель, у которой уже был пин, идёт первой внутри своего кластера — это то, что не даёт смене провайдера утащить диалог на другую модель.
6. **Пин.** Побеждает `{ only: [tag], allow_fallbacks: false }` — один конкретный endpoint. Решение пишется дважды: событием `model-routing/decision` в лог сессии (флаг `ignorable`) и строкой в JSONL-историю `diagnosticsPath` (см. «Что маршрут знает и где это читать»).
7. **Диспетчеризация.** Запрос уходит в `ctx.piAiDispatch` мимо `ctx.llm` — иначе внешний адаптер спроецировал бы историю второй раз и срезал `replayState`. При падении провайдера до первого контент-чанка происходит перерешение, не более `maxReroutes` раз; политика — deny-list `noRerouteCodes`, то есть рероутит любой код, кроме перечисленных ([ADR-0002](adr/0002-reroute-pre-content-provider-failures.md)). Бюджет `maxReroutes` считает **смены кандидата**, а не попытки: пока счётчик отказов не дошёл до `excludeAfterFailures`, перерешение возвращает тот же маршрут, и это ретрай на нём. Скамейка (`excludeAfterFailureMs`) — то, что заставляет перерешение взять другого.

## Судья

Включён, когда тиров не меньше двух: только тогда `auto` появляется в пикере. Вызывается же судья только тогда, когда запрос назвал `auto`, а это не дефолт профиля (см. «Конфигурация»). Сам `auto` описывает **слабейший** тир — вызвавший, который разрешит его против сильнейшего, получил бы окно контекста, которого нет ни у одной реально выбранной модели. Судья — `typesafe/jev-1.13` через Decisions API, закреплён версией намеренно: псевдоним молча переехал бы на новую и все откалиброванные пороги перестали бы значить то, что значили. Пороги: `judgeStartProAt 0.5`, `judgeToProAt 0.6`, `judgeToFlashAt 0.3`. Ответ судьи едет в то же событие решения.

## Снапшоты

Проблема, из-за которой всё это и появилось: **id без версии — не алиас, а самый старый релиз семейства.** На OpenRouter:

| Что написано в тире | Что это на самом деле | Новейший снапшот семейства |
|---|---|---|
| `deepseek/deepseek-v4-pro` | DeepSeek V4 Pro **0423** | `deepseek/deepseek-v4-pro-0813` |
| `deepseek/deepseek-v4-flash` | DeepSeek V4 Flash **0423** | `deepseek/deepseek-v4-flash-0731` |
| `z-ai/glm-5.3` | релиз 20260920 | тот же |
| `z-ai/glm-5.3-flash` | релиз 20260920 | тот же |
| `stealth/space-bunny-alpha` | даты нет | тот же |

Семейство берётся не из display-name, а из поля `canonical_slug`, которое OpenRouter публикует в `GET /models`: для каждой записи там сказано, какой датированный релиз этот id и есть. Записи с общим `canonical_slug` и есть семейство; новейшая дата в нём и есть нужный id. Поэтому `deepseek/deepseek-v4-flash-vision-exp` и `deepseek/deepseek-v4.1-flash` в семейство v4-flash не попадают.

Что это меняет в поведении:

- тир, перечисляющий `deepseek/deepseek-v4-pro`, едет на `-0813` без правки конфига;
- запрос, назвавший `deepseek/deepseek-v4-pro` напрямую (выбор в пикере), резолвится так же — пикер и предлагает id тиров, а «про» — это модель, не релиз;
- два id одного тира, сошедшиеся на одном релизе, схлопываются до одного кандидата;
- каждое перемещение пишется в лог один раз: `"deepseek/deepseek-v4-pro" now resolves to "deepseek/deepseek-v4-pro-0813"`, а в `model-routing/decision` всегда лежит тот релиз, который реально ответил.

Каталог читается не чаще раза в час (`catalogTtlMs`); решения, принятые одновременно, делят одно чтение, а чтение, которое не удалось, отдаёт последний успешный. Первый же отказ без предыдущего чтения **не считается поломкой маршрута**: тир решает под своими id, а в лог уходит одна строка `the OpenRouter model catalog could not be read`.

Обратная сторона, записанная в README пакета: под `latest` новый релиз меняет модель и цену без чьего-либо согласия. Тому, кому такое не подходит, нужен `pinned` — это и есть дефолт.

## Конфигурация

Профиль: `~/.dsh/profiles/web/cordis.patch.yml`, строка `- id: model-routing`. Две ловушки формы, обе тихие, поэтому блок выглядит многословно:

- **строка должна существовать.** Патч по id не находит строку — печатает `patch: entry %C not found` и молча уходит. Строка появляется только потому, что стоит бандл `model-routing-profile`;
- **`config:` заменяет объект целиком**, а не мержит. Отсюда блок `threads-preset` ниже перечисляет все ключи пресета, а не только свои.

Поля, которые задаёт этот профиль:

```yaml
tiers:
  - { name: pro,   models: [ deepseek/deepseek-v4-pro, z-ai/glm-5.3, xiaomi/mimo-v2.6-pro, … ], …, unknownQuantization: reject, free: 'off' }
  - { name: flash, models: [ z-ai/glm-5.3-flash, stealth/space-bunny-alpha, deepseek/deepseek-v4.1-flash, xiaomi/mimo-v2.6-flash, … ], …, free: prefer }
  # каждый тир несёт extraSources — прямые источники рядом с OpenRouter-эндпоинтами:
  # claude-proxy (claude-opus-5 / claude-sonnet-5 через modelMap) и Anthropic-token-plan-sgp
trustedUnknownProviders: [ stealth ]
# список кодов рероута не задаётся: политика — deny-list, по умолчанию запрещены
# только CONTEXT_WINDOW_EXCEEDED, IMAGE_OFFLOAD_REQUIRED и ABORTED (ADR-0002)
efforts: [ high, xhigh, max ]
defaultEffort: high
defaultTier: flash
judgeEnabled: true
judgeModel: typesafe/jev-1.13
presetRoutes:
  - { preset: project, model: pro }
cacheIdleMs: 600000
freeForSubagents: true
# Скамейку кандидата профиль не задаёт: действуют дефолты пакета —
# excludeAfterFailures: 5 и excludeAfterFailureMs: 600000. Счётчик считает
# отказы ПОДРЯД и обнуляется успехом кандидата и истечением скамейки. Пока
# порог не достигнут, перерешение возвращает тот же маршрут — это ретрай на
# нём, а не переезд; maxReroutes считает именно переезды.
snapshotPolicy: latest
diagnosticsPath: /Users/user/Documents/deepseek-harness/default-workspace/session-debug/model-routing-history.jsonl
# diagnosticsMaxBytes профиль не задаёт: действует дефолт пакета, 262144
```

`trustedUnknownProviders` перекрыт на `[ stealth ]`, то есть список из `config.ts` здесь не действует: `unknown` по квантизации принимается только у `stealth`. Список по умолчанию выведен замером и содержит 15 площадок ([MEASUREMENTS.md](MEASUREMENTS.md#квантизации-кто-объявляет-unknown)); сужение до одной записано как открытый вопрос в [STATUS.md](STATUS.md#открытые-баги).

Отдельно стоит посмотреть на строку `agent-default-model` того же профиля. Это **не настройка профиля, а место, куда пишет пикер**: каждый выбор модели в UI проходит через `agentDefaultModel.saveSelection` и перезаписывает эту строку через `configEditor`. Поэтому её значение — последнее, что выбрали руками, и живёт оно до следующего выбора.

Значение `model` задаёт режим: `auto` — судья выбирает ступень, а внутри ступени идёт ранжирование по смешанной цене; имя тира (`pro`, `flash`) — этот тир; конкретный id модели тира — `fixed`, то есть судья не вызывается и ранжируются только провайдеры одной модели. `provider` при этом не обязан быть `tiers`: выбрав модель другого маршрута (например `claude-proxy` / `claude-opus-5`), вы выводите `tiers` из игры — с этого выбора запрос уходит мимо него, решения не пишутся, чип ничего не показывает. Исключение одно: сессия пресета `project`, чей запрос всё равно переписывается на `tiers` / `pro` — но только пока в этой сессии не выставлен явный выбор модели.

Состояние на 2026-10-09 18:40: `provider: claude-proxy, model: claude-opus-5`, то есть маршрут по умолчанию не задействован. Вернуть `auto` можно выбором `Auto` в пикере — он запишет `model: auto`; ручная правка YAML работает так же, но следующий выбор в пикере её затрёт.

Список id **не трогайте при выходе нового релиза** — ради этого `latest` и нужен. Меняйте только если меняется модель или фильтры тира.

## Ловушки

| Что | Чем кончится |
|---|---|
| `model` в `agent-default-model` назван конкретным id вместо `auto` | судья не вызывается, ранжирование идёт по провайдерам одной модели; выглядит как работающий маршрут |
| `provider` в `agent-default-model` назван не `tiers` | маршрут не участвует вовсе: решения не пишутся, чип пуст, а в сессии пресета `project` запрос всё равно уезжает на `tiers` / `pro` |
| Псевдоним `~deepseek/deepseek-pro-latest` в тире | `/endpoints` отдаёт по нему пустой список, ранжировать нечего, тир молча уходит на следующую модель в списке |
| `snapshotPolicy: latest` при недоступном OpenRouter | тир решает под старыми id и говорит об этом в лог — это не поломка, но и не обновление |
| Модель только с `:variant`-id | резолв вернёт вариант: разбираться с платной семантикой `:batch` придётся на месте |
| `unknownQuantization: reject` у нового релиза | провайдеры, не объявившие формат, вылетят; вместо тихой подмены модели будет отказ `no endpoint of tier "…" passes the filters` |

Последнее — единственный из этих случаев, который шумит: остальные молчат и решают не тем.

## Границы

- Работа закоммичена; поверхность конфликтов с апстримом считает [INVENTORY.md](INVENTORY.md).
- Профиль переключён на `latest`, хост перезапущен 2026-10-06: живые решения 2026-10-07 показывают `deepseek/deepseek-v4-pro-0813` в кандидатах и `source: {kind: 'claude-proxy'}` в победителях, то есть политика снапшотов и прямые источники действуют.
- «Победитель всегда `claude-proxy`» верно только для `auto` и тиров: у них прямой источник с фиктивной ценой `1e-12` обгоняет OpenRouter. При выборе конкретной модели тира побеждает OpenRouter-тег (`inference-net/fp8`, `deepinfra/fp8`), а при выборе модели чужого маршрута решения не пишутся вовсе (см. «Конфигурация»).
- Резолв семейства — локальная доработка `llm-pi-ai`; апстрим её не знает, и при отчуждении она едет вместе с `fetchOpenRouterEndpoints` (см. [plans/model-routing.md](plans/model-routing.md)).

## Что маршрут знает и где это читать

Каждое решение пишется дважды. Событие `model-routing/decision` в логе сессии (флаг `ignorable`) несёт сжатую форму: модель и провайдера, `blendedUsdPerToken`, **микс токенов** с указанием, измерен он из сессии или взят из конфига (`mix.source`), **фильтры, под которыми шло ранжирование** (`filters`), число отсевов по каждой причине (`rejections`) и **самый дешёвый отсеянный эндпоинт по каждой причине** (`cheapestRejected`). Последнее отвечает на вопрос «а 50% скидка куда делась» прямо из лога.

Полная таблица кандидатов уходит в файл `diagnosticsPath` (JSONL, одна строка на решение): каждый эндпоинт, который видело ранжирование, с ценами, **скидкой OpenRouter**, замерами и либо рангом, либо причиной отсева. Это история для диагностики: решение недельной давности можно перепроверить по данным, какими они были тогда. Каждая строка ограничена `diagnosticsMaxBytes` (256 КиБ по умолчанию): кандидаты пишутся в порядке ранжирования, не поместившиеся просто отсутствуют — `considered` против `candidates.length` это показывает. Пустой `diagnosticsPath` (дефолт) файл не пишет вовсе.

Что где видно:

| Факт | Где виден |
|---|---|
| Тир и модель | текст чипа в композере |
| Выбор, ждущий следующего запроса | текст чипа: `<tier> · <ответившая> → <следующая>`, плюс строка в `title=` |
| Провайдер, квантизация, граница | только `title=` чипа, то есть при наведении |
| Смена модели или маршрута | строка в транскрипте (узел `model-switch`): обе стороны и граница. Пока ход идёт — видна сразу; у завершённого хода сворачивается в «процесс» вместе со строками ретраев |
| Тир и модель Thread'а | строка ростера (`threadModelLabel`), **без провайдера** |
| Цена хода, проигравшие, отсевы, скидки | JSONL-история (`diagnosticsPath`) и событие в логе сессии |
| Решение, принятое на прошлых ходах | JSONL-история; чип показывает только последнее |

Маршрут может сменить провайдера посреди разговора на `idle`, `failure` или `compaction`; смену видно строкой в транскрипте, а каждое такое решение по-прежнему лежит в истории. Расход по Project считается в токенах (`ProjectTokenUsage`), а не в деньгах, хотя цена за токен в решении и в истории есть.
