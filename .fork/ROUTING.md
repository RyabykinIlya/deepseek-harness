# Model routing — как работает сейчас

Описано 2026-10-04 по коду в этом дереве. Файл отвечает на вопрос «что происходит, когда агент делает запрос». Почему выбран именно такой вариант — в [DECISIONS.md](DECISIONS.md), на каких числах он стоит — в [MEASUREMENTS.md](MEASUREMENTS.md), что осталось сделать — в [plans/model-routing.md](plans/model-routing.md).

Маршрут называется `tiers` и живёт в трёх пакетах: `experimental/model-routing` (host), `experimental/client-ui-model-routing` (чип в композере и страница настроек), `experimental/model-routing-profile` (бандл, вставляющий обе строки). В профиле `web` они стоят через `link:` на это дерево, поэтому пересборка пакета видна сразу.

## Путь запроса

1. **`agent/request`.** Слушатель в `service.ts` переписывает предложение: пресет из `presetRoutes` получает `provider: tiers` и свою модель (`project` → `pro`), а Thread с tier-override получает свой тир. Уровень рассуждения при этом снимается — тир его не выбирал.
2. **Граница.** `boundaryOf` решает, можно ли вообще брать новое решение. Маршрут **не** перерешает каждый ход: смена модели или провайдера убивает prompt-кэш, а ход агента почти целиком кэшированный. Границы: `start`, `failure`, `selection-change`, `compaction`, `idle` (`cacheIdleMs`, по умолчанию 10 минут). Между ними работает пин.
3. **Решение.** Определяется тир: `fixed` (запрос назвал id из списка тира), `tier` (назвал тир) или `auto` — тогда судья решает.

   Разница между тремя случаями больше, чем кажется, и её стоит держать в голове при чтении конфигурации. Только `auto` вызывает судью. Только `auto` и `tier` ранжируют по всем моделям тира: под `fixed` кандидат ровно один (`adapter.ts`, `candidateModels`), и выбор сводится к перебору провайдеров этой одной модели. То есть «дешевейший среди избранных» работает при `auto`, а «дешевейший провайдер названной модели» — при `fixed`.
4. **Снапшоты.** Под `snapshotPolicy: latest` каждый id тира сперва резолвится в новейший снапшот своего семейства. Подробности ниже.
5. **Ранжирование.** По цене смешанной: `cached · cacheRead + fresh · prompt + output · completion`, веса по умолчанию `0.9 / 0.08 / 0.02`. Модель, у которой уже был пин, идёт первой внутри своего кластера — это то, что не даёт смене провайдера утащить диалог на другую модель.
6. **Пин.** Побеждает `{ only: [tag], allow_fallbacks: false }` — один конкретный endpoint. Решение пишется в лог сессии событием `model-routing/decision` с флагом `ignorable`.
7. **Диспетчеризация.** Запрос уходит в `ctx.piAiDispatch` мимо `ctx.llm` — иначе внешний адаптер спроецировал бы историю второй раз и срезал `replayState`. При падении провайдера тег исключается на `excludeAfterFailureMs` и происходит перерешение, не более `maxReroutes` раз.

## Судья

Включён, когда тиров не меньше двух: только тогда `auto` появляется в пикере, и он описывает **слабейший** тир — вызвавший, который разрешит его против сильнейшего, получил бы окно контекста, которого нет ни у одной реально выбранной модели. Судья — `typesafe/jev-1.13` через Decisions API, закреплён версией намеренно: псевдоним молча переехал бы на новую и все откалиброванные пороги перестали бы значить то, что значили. Пороги: `judgeStartProAt 0.5`, `judgeToProAt 0.6`, `judgeToFlashAt 0.3`. Ответ судьи едет в то же событие решения.

## Снапшоты

Проблема, из-за которой всё это и появилось: **id без версии — не алиас, а самый старый релиз семейства.** На OpenRouter:

| Что написано в тире | Что это на самом деле | Новейший снапшот семейства |
|---|---|---|
| `deepseek/deepseek-v4-pro` | DeepSeek V4 Pro **0423** | `deepseek/deepseek-v4-pro-0813` |
| `deepseek/deepseek-v4-flash` | DeepSeek V4 Flash **0423** | `deepseek/deepseek-v4-flash-0731` |
| `z-ai/glm-5.3` | релиз 20260920 | тот же |
| `z-ai/glm-5.3-flash` | релиз 20260920 | тот же |
| `stealth/space-bunny-alpha` | даты нет | тот же |

Семейство берётся не из display-name, а из поля `canonical_slug`, которое OpenRouter публикует в `GET /models`: для каждой записи там сказано, какой датированный релиз этот id и есть. Записи с общим `canonical_slug` и есть семейство; новейшая дата в нём и есть нужный id. Поэтому `deepseek/deepseek-v4-flash-vision-exp` и `deepseek/deepseek-v4.1-flash` в семейство v4-flash не попадают.

Что это меняет в поведении:

- тир, перечисляющий `deepseek/deepseek-v4-pro`, едет на `-0813` без правки конфига;
- запрос, назвавший `deepseek/deepseek-v4-pro` напрямую (выбор в пикере), резолвится так же — пикер и предлагает id тиров, а «про» — это модель, не релиз;
- два id одного тира, сошедшиеся на одном релизе, схлопываются до одного кандидата;
- каждое перемещение пишется в лог один раз: `"deepseek/deepseek-v4-pro" now resolves to "deepseek/deepseek-v4-pro-0813"`, а в `model-routing/decision` всегда лежит тот релиз, который реально ответил.

Каталог читается не чаще раза в час (`catalogTtlMs`); решения, принятые одновременно, делят одно чтение, а чтение, которое не удалось, отдаёт последний успешный. Первый же отказ без предыдущего чтения **не считается поломкой маршрута**: тир решает под своими id, а в лог уходит одна строка `the OpenRouter model catalog could not be read`.

Обратная сторона, записанная в README пакета: под `latest` новый релиз меняет модель и цену без чьего-либо согласия. Тому, кому такое не подходит, нужен `pinned` — это и есть дефолт.

## Конфигурация

Профиль: `~/.dsh/profiles/web/cordis.patch.yml`, строка `- id: model-routing`. Две ловушки формы, обе тихие, поэтому блок выглядит многословно:

- **строка должна существовать.** Патч по id не находит строку — печатает `patch: entry %C not found` и молча уходит. Строка появляется только потому, что стоит бандл `model-routing-profile`;
- **`config:` заменяет объект целиком**, а не мержит. Отсюда блок `threads-preset` ниже перечисляет все ключи пресета, а не только свои.

Поля, которые задаёт этот профиль:

```yaml
tiers:
  - { name: pro,   models: [ deepseek/deepseek-v4-pro, z-ai/glm-5.3 ], …, unknownQuantization: reject, free: 'off' }
  - { name: flash, models: [ deepseek/deepseek-v4-flash, z-ai/glm-5.3-flash, stealth/space-bunny-alpha ], …, free: prefer }
trustedUnknownProviders: [ stealth ]
snapshotPolicy: latest
judgeModel: typesafe/jev-1.13
presetRoutes:
  - { preset: project, model: pro }
```

`trustedUnknownProviders` перекрыт на `[ stealth ]`, то есть список из `config.ts` здесь не действует: `unknown` по квантизации принимается только у `stealth`. Список по умолчанию выведен замером и содержит 15 площадок ([MEASUREMENTS.md](MEASUREMENTS.md#квантизации-кто-объявляет-unknown)); сужение до одной записано как открытый вопрос в [STATUS.md](STATUS.md#открытые-баги).

Отдельно стоит посмотреть на строку `agent-default-model` того же профиля: там стоит `provider: tiers, model: stealth/space-bunny-alpha`. Это `fixed`, а не `auto`, поэтому в обычной сессии судья не вызывается и ранжирование идёт по эндпоинтам одной модели. Автоматический выбор ступени включается заменой `model` на `auto`.

Список id **не трогайте при выходе нового релиза** — ради этого `latest` и нужен. Меняйте только если меняется модель или фильтры тира.

## Ловушки

| Что | Чем кончится |
|---|---|
| `model` в `agent-default-model` назван конкретным id вместо `auto` | судья не вызывается, ранжирование идёт по провайдерам одной модели; выглядит как работающий маршрут |
| Псевдоним `~deepseek/deepseek-pro-latest` в тире | `/endpoints` отдаёт по нему пустой список, ранжировать нечего, тир молча уходит на следующую модель в списке |
| `snapshotPolicy: latest` при недоступном OpenRouter | тир решает под старыми id и говорит об этом в лог — это не поломка, но и не обновление |
| Модель только с `:variant`-id | резолв вернёт вариант: разбираться с платной семантикой `:batch` придётся на месте |
| `unknownQuantization: reject` у нового релиза | провайдеры, не объявившие формат, вылетят; вместо тихой подмены модели будет отказ `no endpoint of tier "…" passes the filters` |

Последнее — единственный из этих случаев, который шумит: остальные молчат и решают не тем.

| Файл | Роль |
|---|---|
| `packages/experimental/model-routing/src/adapter.ts` | маршрут, границы, пин, перерешение, `candidateModels` |
| `packages/experimental/model-routing/src/boundary.ts` | когда можно перерешать |
| `packages/experimental/model-routing/src/select.ts` | фильтры, смешанная цена, ранжирование, `preferModel` |

| `packages/experimental/model-routing/src/family-cache.ts` | кэш каталога с откатом на последний успешный |

| `packages/experimental/model-routing/src/judge.ts` | запрос к Decisions API и пороги |

## Как проверять

```sh
# решение снапшотов на живом каталоге, без приложения
pnpm vitest run packages/experimental/model-routing packages/llm/llm-pi-ai

# покрытие новых модулей обязано быть 100 % пофайлово
pnpm vitest run --coverage --coverage.include='packages/experimental/model-routing/src/family*.ts' packages/experimental/model-routing

# снапшот сессии с этим маршрутом
pnpm run test:snapshot -t tiers
```

Проверено на живом каталоге 2026-10-04 (466 моделей) этим же кодом: pro уезжает на `-0813`, flash на `-0731`, glm и `space-bunny-alpha` остаются.

## Границы

- Изменение **не закоммичено**: инвентарь в [INVENTORY.md](INVENTORY.md) считает только коммиты, поэтому цифры в нём эту работу ещё не видят.
- Профиль переключён на `latest`, но **хост не перезапущен**: работающее приложение собрано до правки. Без перезапуска политика не действует, а лог молчит.
- Резолв семейства — локальная доработка `llm-pi-ai`; апстрим её не знает, и при отчуждении она едет вместе с `fetchOpenRouterEndpoints` (см. [plans/model-routing.md](plans/model-routing.md)).

## Что маршрут знает, но не показывает

Решение пишется в лог целиком: `providerName`, `quantization`, `blendedUsdPerToken`, число рассмотренных эндпоинтов, три ближайших проигравших и теги, исключённые после отказов. До экрана доходит заметно меньше.

| Факт | Где виден |
|---|---|
| Тир и модель | текст чипа в композере |
| Провайдер, квантизация, граница | только `title=` чипа, то есть при наведении |
| Тир и модель Thread'а | строка ростера (`threadModelLabel`), **без провайдера** |
| Цена хода, проигравшие, исключённые теги | нигде |
| Решение, принятое на прошлых ходах | нигде: чип показывает только последнее |

Последняя строка — самая неприятная. Маршрут может сменить провайдера посреди разговора на `idle`, `failure` или `compaction`, и тогда по прокрутке истории уже не узнать, кто отвечал на тот ход, где ответ был плохим, — хотя в логе это записано. Расход по Project считается в токенах (`ProjectTokenUsage`), а не в деньгах, хотя цена за токен в решении есть.
