# Доработка: судья model-routing с тремя тирами (mega/pro/flash)

Задача для реализации в репозитории `deepseek-harness`, пакет
`packages/experimental/model-routing`. Этот документ — функциональное требование;
написано 2026-10-15 по живому коду (см. версии/строки ниже — сверить перед стартом,
пакет меняется).

## Контекст: что уже есть

Конфигурация уже **не** предполагает двух тиров: `tiers` — список любой длины,
и в живом профиле (`~/.dsh/profiles/web/cordis.patch.yml`) с 2026-10-15 три тира —
`mega` (эскалационный), `pro`, `flash`. Всё, что не судья, уже трёхтирно:

- пикер моделей: тиры из конфига, `tiers/mega` выбирается руками;
- `presetRoutes`: `{preset, model}` ссылается на имя тира — может быть `mega`;
- `JudgeRequest.proTier` уже параметризован, схема ответа судьи уже generic
  (`probabilities: Record<string, number>`, `judge.ts:120-136`);
- `defaultTier`, `judgeProTier`, `judgeFlashTier` — строки в конфиге.

Единственное бинарное место — логика вердикта и вопрос судьи.

| Шов | Файл | Что сейчас |
|---|---|---|
| Вопрос судьи | `judge.ts:32-53` `judgeQuestions` | `criteria` из ровно двух тиров: `flash`, `pro` (из настроек) |
| Чтение вероятностей | `judge.ts:255-264` | только `pPro = probabilities[request.proTier]` |
| Перевод вердикта в тир | `judge.ts:283+` `tierFromVerdict` | правила только flash↔pro: `start-pro/start-flash/to-pro/to-flash` (+ precision, low-confidence, keep) |
| Пороги | `config.ts` | `judgeStartProAt`, `judgeToProAt`, `judgeToFlashAt`, `judgeProTier`, `judgeFlashTier` — volatile, с дефолтами |
| Критерии промпта | `config.ts` | `judgeFlashCriteria`, `judgeProCriteria`, общий `judgeTierInstructions` |
| Тесты | `tests/judge.spec.ts` | на `judgeQuestions` и `tierFromVerdict` (бинарные случаи) |

## Цель (функциональные требования)

**FR-1. Третий тир у судьи — опциональный.** Конфигурационное поле
`judgeMegaTier: string` (volatile, без дефолта — пустая строка = трёхрежимность
выключена, поведение байт-в-байт как сейчас). Пустое значение не ломает
существующие развёртывания и существующие тесты.

**FR-2. Пороги эскалации — отдельные поля**, не переиспользование pro-порогов:
`judgeToMegaAt: number` и `judgeMegaDownAt: number` (volatile, без дефолта;
заданы ⇒ действуют). Семантика: вероятность мега-тира у вердикта.

**FR-3. Вопрос судьи включает третий тир**, когда `judgeMegaTier` непуст:
`criteria` получает `[flash, pro, mega]` с новым полем `judgeMegaCriteria`
(volatile string, дефолта нет — обязателен при включённом режиме, иначе fail
loud при загрузке конфига). Двухтирный режим шлёт ровно как сейчас.

**FR-4. `tierFromVerdict` — трёхуровневая лестница, cheapest-first порядок
правил сохраняется** (каждое правило — про конкретный переход; порядок важен,
как сейчас: precision → low-confidence → старт → переходы). Новые правила:
- старт сессии: `pMega ≥ judgeStartMegaAt` → mega (новое поле `judgeStartMegaAt`,
  без дефолта); иначе как сейчас (`pPro ≥ judgeStartProAt` → pro);
- эскалация: `current === pro && pMega ≥ judgeToMegaAt` → mega (rule `to-mega`);
- понижение: `current === mega && pMega ≤ judgeMegaDownAt` → pro (rule
  `mega-to-pro`). Из mega понижение идёт в pro, не сразу во flash — лесенка
  по соседним ступеням, скачков нет.
- `judge-rule` в проекции/событиях: новые правила (`to-mega`, `mega-to-pro`,
  `start-mega`) попадают в union типа так же, как существующие.

**FR-5. Вероятности читаются поимённо**: `pPro` и `pMega` из
`probabilities[request.proTier]` / `probabilities[megaTier]`. Вердикт без
вероятности мега-тира при включённом режиме — не ошибка: отсутствие = 0 (как
сейчас `pPro`), но `JudgeVerdict` получает поле `pMega` рядом с `pPro`, чтобы
диагностика решений (diagnosticsPath JSONL) показывала обе вероятности.

**FR-6. Названия тиров не хардкодятся.** `mega` в правилах — это значение
`judgeMegaTier` из конфига, не литерал. Поле может называться иначе (например,
`ultra`), правила от этого не меняются. Это уже так для pro/flash — сохранить
инвариант.

**FR-7. UI и локали.** Настройки model-routing (`client-ui-model-routing`):
если страница рисует поля судьи списком из конфига — добавленные поля появляются
сами; если поля перечислены вручную — добавить `judgeMegaTier`,
`judgeMegaCriteria`, `judgeStartMegaAt`, `judgeToMegaAt`, `judgeMegaDownAt`.
Все новые строки — через локали (`verify-client-ui-i18n`), RU+EN+ZH.

**FR-8. Обратная совместимость — жёсткое требование.** Конфиг без мега-полей
(нынешние развёртывания) даёт ровно нынешнее поведение: те же правила, те же
промпты, те же ответы судьи.

## Экономическое обоснование (почему отдельные пороги, а не «выше pro»)

Mega-модели в живом развёртывании — самые тощие квоты подписки OpenCode Go
(`kimi-k3` ≈ 490 запросов/мес, `qwen3.8-max` ≈ 810). Автоэскалация судьи
в мега по общему порогу сожжёт их за дни. Отдельные `judgeToMegaAt` (заведомо
выше `judgeToProAt`) — единственный способ сделать «редко, но метко»
конфигурируемым, не хардкодом. В дефолтах порогов намеренно отказано
(см. FR-2): правильное значение знает только развёртывание.

## Требования к реализации (по AGENTS.md репозитория)

- Новые поведения — через конфигурационные поля со схемой (`Config`), без
  `DEFAULT_*`-констант; misconfiguration — fail loud при загрузке (например,
  `judgeMegaTier` непуст, а `judgeMegaCriteria`/пороги пусты — ошибка загрузки,
  а не молчаливый двухрежим).
- Всё, что видит модель, воспроизводимо из лога: новые правила и `pMega` —
  в событии/проекции решения (см. FR-4/FR-5), `ignorable: true` где уместно.
- Изменение поверхности конфигурации — проверить `dsh-create-upgrade-guide`,
  README пакета и doc-sync для затронутых поверхностей; snapshot-тесты на
  модельно-видимые изменения.
- Сверить, что `JudgeRule` (union) и его потребители (`projection.ts`,
  диагностика, chip/labels в UI) не зашиты на два значения.

## Открытые вопросы (решить до/при реализации, не угадывать)

1. **Значения порогов для живого профиля** — предлагает развёртывание, не код.
   Стартовая точка для подбора: `judgeStartMegaAt` ≈ 0.9, `judgeToMegaAt` ≈
   0.85, `judgeMegaDownAt` ≈ 0.3 — с обязательной калибровкой по
   `diagnosticsPath` (вероятности уже пишутся; посмотреть распределение pPro
   на реальной истории и выбрать порог по хвосту).
2. **Текст `judgeMegaCriteria`** — формулировка критерия «задача заслуживает
   мега» (длинный горизонт, многошаговость, цена ошибки). Черновик — у
   владельца.
3. **Может ли судья стартовать сессию сразу в mega** (`start-mega`) — в FR-4
   включено (`judgeStartMegaAt`); если покажется слишком агрессивным,
   поле оставить, но порог задать высоким. Не выкидывать правило.
4. **Subagent-режим** (`freeForSubagents`) — субагенты остаются на своём
   маршруте, мега их не касается; проверить, что это так.

## Приёмка

1. Конфиг без мега-полей ведёт себя ровно как до правки (FR-8).
2. Включённый режим: судья получает третий критерий, вердикт без вероятности
   мега-тира читается как «не мега», не как ошибка; решения пишутся в
   `diagnosticsPath` с `pPro`/`pMega` и правилами `to-mega`/`mega-to-pro`.
3. Прогон живого профиля (вручную): сессия с `judgeMegaTier: mega` и
   порогами из п.1 открытых вопросов — судья отвечает, лестница flash→pro→mega
   работает в обе стороны.
4. `pnpm run test`, `typecheck`, `lint`, doc-sync по затронутым поверхностям —
   чисто.
