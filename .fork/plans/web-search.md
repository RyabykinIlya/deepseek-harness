Три провайдера поиска: Brave, DuckDuckGo, Tavily. Плюс разобранный и отложенный четвёртый — Яндекс, см. [ниже](#четвёртый-провайдер-яндекс--решение-не-принято).

## Состояние

**Работает** (проверено живым вызовом 2026-10-07, провайдер `tavily` отвечает), тесты зелёные. Три новых пакета: `packages/web/web-search-brave`, `web-search-duckduckgo`, `web-search-tavily`.

В рабочем профиле выбран `tavily` (`searchProvider: tavily`), то есть на практике используется он. Линт по своим пакетам — 0 ошибок (закрыто 2026-10-04).

## Чем связан с ядром

Это самый дешёвый случай из трёх плагинов — правки списка id и карточки настроек почти целиком косметические. Исключение — `web-fetch-http`: там guard-логика fetch, а не косметика, и это отдельная фича Web fetch, строка в таблице ниже.

| Апстримный файл | Что добавлено | Обязательно? |
|---|---|---|
| `packages/web/web/src/index.ts` | `WEB_SEARCH_PROVIDER_IDS`, `WEB_FETCH_PROVIDER_IDS` и типы вокруг них | **нет** |
| `packages/client/ui-settings-web-search/*` (7 файлов) | рендер новых провайдеров в карточке настроек | нет, но без этого их не выбрать мышью |
| `packages/web/web-fetch-http/*` (4 файла) | `trustedProxyAddressRanges`: Config-поле и его JSDoc, `compileTrustedAddressRanges` и проверка в guard'е (`isPublicIpAddress` / `resolvePublicAddresses` / `isNonPublicIpLiteral`), применение в `requestOnce`, регрессионные тесты. Это отдельная фича Web fetch, а не web-search | **да**: без неё fetch через transparent-proxy в fake-ip режиме падает на непубличном адресе (`URL hostname "..." resolves to a non-public IP address`). Решение — [../DECISIONS.md](../DECISIONS.md) (раздел «Web fetch»), инвентаризация — [../INVENTORY.md](../INVENTORY.md) |

### Почему список id не обязателен

JSDoc самого `WEB_SEARCH_PROVIDER_IDS` отвечает на это прямо: список — это *известные* id, а не *принимаемые*. `WebRuntime` регистрирует id любого плагина, и конфигурация, назвавшая отсутствующий в списке id, обязана загрузиться и упасть на выборе с `WEB_PROVIDER_CONFIGURED_MISSING`, а не быть отвергнутой схемой.

То есть **регистрация провайдера уже работает без правок ядра**. Список нужен ровно для одного: чтобы страница настроек показала провайдера в выпадашке. Это выбор между «правка ядра» и «провайдер настраивается из `cordis.patch.yml`, а не мышью».

## Четвёртый провайдер: Яндекс — решение не принято

Рассматривался как дополнение к Tavily: RU-сегмент против англоязычного веба. Сравнение и три формы маршрутизации записаны в [../DECISIONS.md](../DECISIONS.md#web-search); решения нет, выбор отложен.

Что стоит знать при возврате к вопросу, чтобы не выяснять заново:

- **Пакета нет.** Регистрация нового провайдера правок ядра не требует (см. «Почему список id не обязателен» выше) — `WEB_SEARCH_PROVIDER_IDS` нужен только для выпадашки в карточке.
- **Два креденшла вместо одного.** Tavily знает один ключ; Яндексу нужны ещё `folderId`, и `available()` обязан проверять оба.
- **Ответ — XML в base64**, а не JSON: нужен XML-парсер как новая зависимость.
- **Доки под captcha.** `yandex.cloud` редиректит на `aistudio.yandex.ru`, который из этой сети отдаёт captcha (проба 2026-10-07), поэтому проверять поведение API придётся живым вызовом с ключом, а не чтением документации.

Ключи у автора форка есть, так что проверяемость не блокер — блокер только нерешённый вопрос «нужна ли маршрутизация вообще».

## Замечание

Если снятие правки `WEB_SEARCH_PROVIDER_IDS` подтвердится, web-search переходит из «почти» в «чисто» — три пакета без единой апстримной правки. Это первый кандидат на отчуждение: дешевле всех и даёт проверенный на практике шаблон для остальных — именно поэтому установка на чистый профиль начинается с него (приоритет 10 в [../STATUS.md](../STATUS.md#приоритеты)).
