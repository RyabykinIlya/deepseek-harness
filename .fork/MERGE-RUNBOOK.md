# Обновление ядра из апстрима

Процедура на **каждое** подтягивание апстрима — без привязки к конкретному релизу. Ничего, что зависит от номера версии, здесь не записано: числа перемеряются командами, а не переписываются руками.

Три принципа, из которых выведены все шаги:

1. **Работа идёт не в том чекауте, который обслуживает сессию** — в отдельном worktree. Почему и как — [ADR-0003](adr/0003-merge-in-worktree-with-fast-forward-cutover.md).
2. **Генерируемое не мержится, а перегенерируется:** до мержа берём апстримную копию, после мержа генерируем своё ([шаг 1](#1-выкинуть-генерируемое-из-своей-ветки), [шаг 3](#3-перегенерировать)).
3. **Мерж применяется fast-forward'ом.** Подмены файлов нет, поэтому путь чекаута не меняется и всё, что на него ссылается абсолютно, переживает обновление.

Сколько работы предстоит в этот раз — перемеряется командами из [шага 6](#6-обновить-замеры) и записывается в [INVENTORY.md](INVENTORY.md). В самом ранбуке этих чисел нет намеренно.

## 0. Подготовка: заморозка и worktree

```sh
git fetch origin --tags

# Что приехало и насколько далеко:
git rev-list --count HEAD..origin/master
git log --oneline HEAD..origin/master | head -30
git tag --sort=-creatordate | head -5        # какой релиз подъехал

# Дерево должно быть чистым — см. ниже.
git status --porcelain                        # ожидается пустой вывод
```

**Заморозка обязательна.** `git worktree` ветвится от коммита и незакоммиченное не наследует, а `merge --ff-only` при непустом дереве откажется. Незакоммиченную работу — в коммит или в stash.

Если дерево пишется прямо сейчас (другая сессия, редактор) — **дождаться, пока запишут**. Коммит в середине чужой правки фиксирует полуготовое состояние.

```sh
# Запомнить оба пути: они понадобятся при проверке приложения.
MAIN=$(git rev-parse --show-toplevel)
STAMP=$(date +%Y%m%d)
ROLLBACK=$(git rev-parse HEAD)          # точка отката

git worktree add "$MAIN/.worktrees/merge-$STAMP" -b "merge/$STAMP"
cd "$MAIN/.worktrees/merge-$STAMP"
WT=$(pwd)

git remote -v                            # origin обязан быть апстримом
```

Каталог `.worktrees/` уже в `.gitignore`, а glob'ы воркспейса (`packages/*/*`, `apps/*`, `vendor/*` и т. д.) его не подхватывают.

**Если `origin` внутри worktree указывает не туда** — не править `remote`, а брать точку расхождения явным SHA ([шаг 6](#6-обновить-замеры)): в worktree клона форка `origin/master` может оказаться мастером форка, и сравнение пойдёт с самим собой.

**Что прочитать до разбора.** Апстрим мог изменить внешние поверхности:

```sh
git diff --name-only HEAD..origin/master -- docs/upgrade-guide | sed 's|/[^/]*$||' | sort -u
```

**Если `SESSION_FORMAT_VERSION` вырос** — сверить с [DECISIONS.md](DECISIONS.md), где записано, что значит несовпадение, и добавить в окно вырезки миграцию сессий:

```sh
grep -n "SESSION_FORMAT_VERSION = " packages/core/session/src/types.ts
git show origin/master:packages/core/session/src/types.ts | grep -n "SESSION_FORMAT_VERSION = "
```

Все шаги ниже (1–5) выполняются **внутри worktree**. Основной чекаут в это время не трогается ни на файл.

## 1. Выкинуть генерируемое из своей ветки

Берём апстримную версию всего, что выводится из кода: конфликтовать там не с чем, содержимое всё равно перезапишется на шаге 3.

**Список не писать руками — он уже устаревал.** Набор выводится из пар `gen-*`/`verify-*` в `package.json`: у каждого генератора есть проверяющий его `--check`-гейт.

```sh
# Все генераторы и наличие их гейта:
node -e "const s=require('./package.json').scripts;
for(const k of Object.keys(s).filter(k=>/^gen-/.test(k)))
  console.log(k.padEnd(30), Object.keys(s).includes('verify-'+k.slice(4)) ? 'paired' : '—')"

# Куда пишет конкретный генератор:
grep -nE "^(export )?const (OUT|[A-Z_]+_(OUT|PATH|FILE|SOURCE|ENTRY)) *=" scripts/gen-<имя>.ts
```

Взять апстримную копию **всех** путей, которые эти генераторы пишут, плюс файлы состояния, которые порождаются не кодом, а гейтами:

```sh
git checkout origin/master -- \
  <каждый путь из списка выше> \
  pnpm-lock.yaml THIRD_PARTY_NOTICES.md \
  scripts/no-unknown-casts.baseline.json \
  $(git ls-files '*.i18n.yaml')
```

Покрытие по видам:

- **Каталоги и графы** (`docs/*catalog*`, `docs/graph-atlas.md`, `docs/module-graph*`, `docs/capability-seams*`, `docs/event-producer-consumer*`, `docs/agent-lifecycle.md`, `docs/tool-execution-pipeline.md`, `apps/cli/composition.md`, `docs/cordis-api/`) — генерируются обходом `packages/*/*/src/**`.
- **Сгенерированный код** (`known-event-types.ts`, оба `api-catalog.ts`, `slot-catalog.ts`, `official-bundles.generated.ts`, `session-format-catalog/src/generated.ts`, `workflow-ptc/src/guest*.ts`, `references/packages.md`) — то же самое в `.ts`.
- **`tsconfig.base.json`** — сгенерирована только зона алиасов; свои строки лежат вне неё и возвращаются на шаге 2 как обычная точка регистрации.
- **`pnpm-lock.yaml`, `THIRD_PARTY_NOTICES.md`** — выводятся из манифестов.
- **`.i18n.yaml`** — перезаписываются гейтом парности на шаге 3.
- **`scripts/no-unknown-casts.baseline.json`** — инвентарь приведений к `unknown`, приводится к нашему дереву через `--prune`. Апстримная копия обязательна: иначе снятые нами приведения читаются как добавленные.

**`snapshots/` сюда не входит и никогда не должен войти.** Часть корпуса записана вручную (`recording: authored`), потому что писалась без ключа, и `test:snapshot:record` их не восстановит — он требует живой модели. Снапшоты мержатся как обычный код, построчно. Сколько именно записано руками:

```sh
grep -rl "recording: authored" snapshots | wc -l
```

## 2. Мерж

```sh
git merge origin/master
```

Разбор конфликтов — по категориям [INVENTORY.md](INVENTORY.md). Практически остаются две:

- **Точки регистрации** (`tsconfig.*.json`, `pnpm-workspace.yaml`, `scripts/*`, `lefthook.yml`) — взять апстримную версию и вернуть свои строки. Свои строки видны так:
  ```sh
  git diff origin/master -- tsconfig.host.json
  ```
- **Правки апстримных пакетов** — читать оба варианта. Если апстрим переписал функцию, которую мы правили, своя правка переносится заново. Это и есть настоящая цена мержа; уменьшает её план отчуждения в [plans/](plans/).

> **Правило file-URL строк (урок мержа alpha.2).** Строки пресетов/бандлов, указывающие модули путями `file://` (тестовые `source()`-фикстуры), лоадер грузит нативным импортом Node (strip-only, без vite-трансформации): parameter properties и декораторы там не парсятся, а ошибка импорта глотается в `ctx.logger` и видна лишь как `never started` в аудите. Проверять нативным импортом все модули, достижимые из таких строк:
>
> ```sh
> node --input-type=module -e "import('./packages/<путь>/src/index.ts').then(() => console.log('OK')).catch(e => console.log('FAIL', String(e.message).split('\n')[0]))"
> ```
>
> Симптом для поиска: `never started` при живых остальных строках той же композиции.

Приём, который экономит время: для файла из второй категории сначала посмотреть, что сделал апстрим, и только потом свою правку.

```sh
git log --oneline HEAD..origin/master -- <путь>   # что апстрим менял здесь
git diff HEAD...origin/master -- <путь>           # и как именно
```

## 3. Перегенерировать

Сначала зависимости, затем все генераторы с их гейтами:

```sh
pnpm install

node -e "const s=require('./package.json').scripts;
for(const k of Object.keys(s).filter(k=>/^gen-/.test(k)))
  if(Object.keys(s).includes('verify-'+k.slice(4))) console.log(k)" | while read g; do
    pnpm run "$g" || exit 1
  done
```

**Если генератор падает — это настоящая ошибка в коде, а не шум мержа.** Разбирать до конца: гейт входит в `doc-sync`, то есть в CI.

Затем — два файла состояния. У обоих есть оговорка, потому что они зависят от нашего дерева, а не только от апстрима:

```sh
# Парность переводов: записывать ТОЛЬКО затронутые пары, не --all.
pnpm run verify-translation-pairing --write <путь к изменённому .md>

# Инвентарь приведений к unknown.
pnpm run verify-no-unknown-casts --prune
```

> **`--write --all` не использовать как слепой шаг.** Он падает на любой паре, где расхождение было до мержа. В форке такие пары есть и к мержу отношения не имеют, поэтому проверять состояние нужно до, а не после:
>
> ```sh
> pnpm run verify-translation-pairing --list | grep -vE '^ok|^$'
> ```
>
> Всё, что этот вывод перечислит до мержа, — существующий долг, а не следствие обновления. `--write` по конкретному пути записывает только ту пару, которую вы действительно привели в порядок; чинить чужой долг в окне мержа не нужно.

Порядок, который важен: **`--prune` — после того, как сняты все свои приведения.** Гейт проверяет добавленные раньше устаревших и падает на добавленных, не дойдя до устаревших.

Проверить, что всё сошлось:

```sh
node -e "const s=require('./package.json').scripts;
for(const k of Object.keys(s).filter(k=>/^verify-/.test(k)))
  if(Object.keys(s).includes('gen-'+k.slice(7))) console.log(k)" | while read v; do
    pnpm run "$v" || echo "FAILED: $v"
  done
```

## 4. Проверить

Минимум, который ловит разъехавшееся после мержа:

```sh
pnpm run typecheck
pnpm run lint
pnpm run test
```

Затем точечно по затронутым пакетам — по конфликтам из [шага 2](#2-мерж):

```sh
# Пакеты, которых коснулся мерж (база мерж-коммита против результата):
git diff --name-only ORIG_HEAD HEAD | grep -E '^(packages|apps)/' | cut -d/ -f1-3 | sort -u
pnpm vitest run <эти пакеты>
```

**И обязательно — запуск приложения.** Типы и тесты не ловят класс ошибок «читает сервис, не объявленный в своей области»: тестовый `TestRemote` подменяет его обычным свойством объекта, а в приложении это падает.

Проверка идёт на **изолированном `DSH_HOME`** — иначе второй экземпляр тронет живые сессии:

```sh
# $MAIN и $WT заданы на шаге 0.
PROBE=/tmp/dsh-merge-home
mkdir -p "$PROBE/profiles"
cp ~/.dsh/.credentials.yaml ~/.dsh/.env "$PROBE/" 2>/dev/null
cp -R ~/.dsh/profiles/web "$PROBE/profiles/"

# Профиль внутри копии должен смотреть на ЭТОТ worktree, иначе проверка пойдёт
# по старым исходникам и ничего не докажет:
sed -i '' "s|$MAIN|$WT|g" "$PROBE/profiles/web/package.json"
grep -o 'link:[^"]*' "$PROBE/profiles/web/package.json"   # ожидаются пути в $WT

# ОБЯЗАТЕЛЬНО: node_modules профиля — симлинки на абсолютные пути, и `cp -R`
# сохраняет их как есть, то есть на $MAIN. Без переустановки второй экземпляр
# загрузит СТАРЫЙ код, а проверка покажет зелёный результат на непроверенном
# дереве. Переустановка идёт из локального стора и занимает секунды.
rm -rf "$PROBE/profiles/web/node_modules"
( cd "$PROBE/profiles/web" && pnpm install --ignore-scripts )

# Убедиться, что симлинки больше не смотрят на $MAIN:
find "$PROBE/profiles/web/node_modules" -maxdepth 3 -type l -exec readlink {} \; \
  | grep -c "deepseek-harness/packages" || echo "0 — все ведут в $WT"

DSH_HOME="$PROBE" pnpm dsh web --no-open --port 3099
```

В живом приложении проверить: консоль без ошибок, существующая сессия открывается, новая создаётся, наши маршруты отвечают, карточки и бандлы на месте.

После проверки временный домашний каталог снести — в нём лежит копия учётных данных:

```sh
rm -rf "$PROBE"
```

## 5. Вырезка — окно простоя

Единственное время, когда работающий harness останавливается. Запускается **из обычного терминала, не из сессии агента**: перезапуск на рабочем порту гасит GUI, в котором эта сессия живёт.

```sh
cd "$MAIN"
git status --porcelain          # должно быть пусто
# остановить dsh
git merge --ff-only "merge/$STAMP"
pnpm install && pnpm run build
# запустить dsh и повторить проверку приложения
```

Порядок обязателен: `pnpm install` под работающим процессом переписывает `node_modules`, который этот процесс уже держит открытым.

### Первая загрузка после вырезки

Три известных ловушки, все проявляются уже после зелёного `build`:

1. **Typert-артефакты.** `tsc -b` только читает `lib/typert.*`, не генерирует их. На дереве, где `lib/` отстал от исходников (чистый клон, `pnpm run clean`, работа с прошлого дня), `build` падает на `TS2307 .../remote` или `TS2339` в typert-namespace. Сгенерировать перед сборкой:

   ```sh
   node --import tsx/esm scripts/generate-typert.ts
   ```

   На чистом дереве порядок тот же: `generate-typert` (или `build:typecheck`) до `build`, потому что gate `host-src` Typert-артефактов не создаёт.

2. **Пины плагинов в профиле.** `~/.dsh/profiles/web/package.json` держит часть плагинов не симлинками, а точными версиями с npm. После подъёма версии рантайма такие плагины лоадер отключает (`Plugin ... is incompatible with dsh ...`): их peer-зависимости `@deepseek-ai/dsh-*` запинены на прежний релиз. Лечение — поднять пин до новой опубликованной версии и `pnpm install` в каталоге профиля. `dsh plugin allow-version` — только временное обходное решение.

3. **Профильный YAML.** Ручные правки `cordis.patch.yml` валидируются схемой при загрузке, и один невалидный плагин отчитывается одной строкой (`N entry did not activate`), а ломается всё, что через него: например, `metadataUserId` в llm-pi-ai — `z.string()`, и блочный YAML-mapping вместо кавыченной строки убивает сервис `piAiDispatch`, а наверх всплывает далёкое `route ... service piAiDispatch is absent`. При любом «слетели модели» первым делом искать ValidationError и отключённые entry в выводе загрузки, а не в пакете, на который указывает ошибка.

**Признаки, при которых откат обязателен:** приложение не стартует; маршрут не отвечает; существующая сессия падает на версии формата.

```sh
git reset --hard "$ROLLBACK" && pnpm install && pnpm run build
```

Пересборка при откате обязательна: после `reset` собранное в `lib/` не соответствует исходникам.

После успешной вырезки worktree снять — он держит свой `node_modules`:

```sh
git worktree remove "$WT"
git branch -d "merge/$STAMP"
```

## 6. Обновить замеры

Команды замера — в конце [INVENTORY.md](INVENTORY.md). Записать туда фактические цифры, заменив прежние, и назвать причину изменения: выросла поверхность из-за новой фичи или упала из-за отчуждения.

Заодно дописать в [MEASUREMENTS.md](MEASUREMENTS.md), сколько занял мерж — по стадиям, а не одним числом. Через два-три релиза это единственный способ понять, движется ли отчуждение.

## Сколько ждать

Гейты идут минутами, и это не зависание. Точные числа зависят от машины и лежат в [MEASUREMENTS.md](MEASUREMENTS.md). Порядок величин:

| Гейт | Порядок |
|---|---|
| `verify-package-readme-summaries`, `verify-concrete-terms`, `verify-doc-budgets` | секунды |
| `verify-package-readme-model-experience`, `verify-repository-references` | десятки секунд |
| `verify-type-equiv`, `verify-md-links`, `verify-translation-pairing` (весь корпус) | минуты |
| `test:docs` (агрегат) | десятки минут — **локально не гонять**, это делает CI |

Отсюда практика: точечные гейты — по затронутым файлам (`pnpm run verify-translation-pairing <путь к .md>` — секунды вместо минут), агрегат `test:docs` оставляется CI.

## Если мерж не влез в сессию

Мерж можно прервать и продолжить, не теряя работы: конфликты разрешаются в worktree и коммитятся частями.

```sh
git merge --abort                 # отменить незавершённый мерж
git status                        # на чём остановились
git add <разобранные файлы> && git commit   # зафиксировать разобранную часть
git merge --continue              # продолжить
```

Worktree остаётся на месте со всем состоянием, основной чекаут всё ещё не тронут. Поэтому прерывание безопасно в любой момент — это и есть смысл вынесенной подготовки.

## Что делать с правками ядра

Каждая правка апстримного пакета должна иметь исход. Три допустимых:

1. **В апстрим.** Отдельный маленький PR. Подходит для самодостаточного шва.
2. **Вендорить.** Перенести в свой пакет. Подходит, если код не обязан жить в ядре.
3. **Держать локально.** Допустимо, но причина записывается в [plans/](plans/), иначе через три мержа никто не вспомнит, зачем эта правка.

Правка без одного из трёх исходов — это та, которая и создаёт боль при каждом обновлении. Исход каждой нынешней правки записан в [plans/](plans/), причина появления — в [DECISIONS.md](DECISIONS.md), вклад в поверхность — в [INVENTORY.md](INVENTORY.md).
