# Принятые решения

Почему плагины устроены так, а не иначе. Здесь только то, что **не выводится из кода**: код говорит, что происходит, а этот файл — почему выбран именно такой вариант и что было отвергнуто.

Решения перенесены сюда 2026-10-04 из рабочих документов двух сессий разработки, которые лежат вне репозитория (`default-workspace`, см. [README.md](README.md#где-исходные-документы)). До переноса на них ссылались комментарии в коде вида `§19 №1`, `§B.1`, `C8` — эти ссылки уезжали в `lib/types/*.d.ts` и в публичные README, указывая на документ, которого читатель не видит. Заменять их надо на ссылки сюда.

Числа, на которых стоят решения, — в [MEASUREMENTS.md](MEASUREMENTS.md).

## Web fetch

### Доступ к локальным адресам — объявленный диапазон, а не флаг

Задача — fetch до сервиса на этой машине или в LAN (локальный dev-сервер, NAS, страница админки роутера). Штатный guard отвергает любой непубличный адрес, и это правильно: он существует, чтобы ответ DNS не увёл запрос к `127.0.0.1` или в RFC1918.

| Вариант | Почему отвергнут |
|---|---|
| Логический флаг `allowLocal: true` | Открывает разом loopback, RFC1918, link-local и CGNAT — то есть всю поверхность, ради которой guard и стоит. Не отличить dev-сервер от чужого сервиса на том же хосте |
| Белый список хостов (`localhost`, имена) | Имя разрешается через DNS в момент запроса; guard проверяет адрес, а имя можно переопределить в hosts. Проверка имени — не проверка адреса |
| **Объявленный CIDR-диапазон** (принято) | Оператор называет ровно те блоки, которые считает своими. Всё вне их остаётся закрытым: объявление loopback не открывает RFC1918, и это покрыто тестом |

Разворот сделан в апстримном пакете `packages/web/web-fetch-http` (`trustedProxyAddressRanges`, компиляция CIDR в `network.ts`, применение в provider), потому что расширить guard извне нельзя — адрес проверяется внутри самой функции запроса. Это категория B инвентаря: точка входа конфигурации, а не обход.

Практическая цена: объявленный блок перестаёт быть барьером для **своего** диапазона. Запись в профиле — по строке на диапазон в `web-fetch-http`, каждая со своим комментарием; удаление строки возвращает guard для диапазона. Имя `trustedProxyAddressRanges`, а не `allowLocal`, стоит по той же причине, по которой решение отвергло флаг: значение — это блоки, а не разрешение.

Список должен быть **полным для этой машины**. Когда transparent-proxy работает в режиме fake-ip/TUN, системный DNS отвечает на каждый домен синтетическим адресом из пула `198.18.0.0/15` (замер 2026-10-05: `dns.lookup('claude.com')` → `198.18.2.112`), и без этого блока падает fetch до любого сайта. Итог для этой машины: LAN-диапазоны `127.0.0.0/8`, `::1/128`, `192.168.0.0/16`, `10.0.0.0/8` плюс fake-ip пул `198.18.0.0/15`.

Строка `config:` в патче профиля **заменяет весь config строки бандла целиком**, глубокого слияния нет — это уже записано комментарием в самом `~/.dsh/profiles/web/cordis.patch.yml` применительно к `threads-preset`. Поэтому частичное перечисление молча удаляет диапазоны бандла: `packages/bundle/base/cordis.patch.yml` несёт дефолт `web-fetch-http.trustedProxyAddressRanges: [198.18.0.0/15]`, а живой профиль перечисляет свою строку `web-fetch-http` только с LAN-диапазонами и тем самым теряет `198.18.0.0/15`. Живые пробы 2026-10-05: `web_fetch http://127.0.0.1:48777/` прошёл, `web_fetch https://claude.com/blog/projects-redesigned` упал с ошибкой про non-public IP — LAN-диапазоны профиля активны, а fake-ip пул в живом конфиге отсутствует.

Исправление, применённое вне репозитория: в список `trustedProxyAddressRanges` строки `web-fetch-http` в `~/.dsh/profiles/web/cordis.patch.yml` добавлен `198.18.0.0/15`; после правки `web_fetch` до `claude.com` проходит (HTTP 200).

## Web search

### Маршрутизация поиска: выбор провайдера — свойство деплоя, а не запроса

Часть запросов лучше обслуживает Яндекс (RU-сегмент), часть — Tavily (в первую очередь англоязычный веб). Вопрос не в том, какой провайдер лучше, а в том, **где стоит выбор**: на уровне деплоя, внутри провайдера или в самом запросе.

Seam `ctx.web` (`packages/web/web/src/index.ts`) разрешает провайдера на каждый вызов, но из одного значения:

| Что задано | Исход вызова |
|---|---|
| id, зарегистрирован и `available()` | обслуживает он |
| id, но не зарегистрирован | `WEB_PROVIDER_CONFIGURED_MISSING` |
| id, зарегистрирован, `available()` ложно | `WEB_PROVIDER_CONFIGURED_UNAVAILABLE` |
| ничего, пригодный ровно один | обслуживает он |
| ничего, пригодных несколько | `WEB_PROVIDER_AMBIGUOUS` |
| ничего, пригодных нет | `WEB_PROVIDER_UNAVAILABLE` |

Источник значения — `web.searchProvider` (эквивалент — `$DSH_WEB_SEARCH_PROVIDER`), то есть строка профиля или страница настроек. Перехода на другого провайдера при отказе нет намеренно: иначе отказ или лимит одного бэкенда молча менял бы источник результатов. В `WebSearchRequest` — только `query` и `maxResults`: ни языка, ни региона, ни имени провайдера запрос не несёт, поэтому per-query маршрутизации в текущем словаре не существует.

### Tavily против Yandex Search

|  | Tavily | Yandex Search API v2 |
|---|---|---|
| Эндпоинт | `POST https://api.tavily.com/search` | `POST https://searchapi.api.cloud.yandex.net/v2/web/search` |
| Аутентификация | `Authorization: Bearer <key>` — одно значение | `Authorization: Api-Key <key>` плюс `folderId` в теле — два значения |
| Тело запроса | `query`, `max_results` | `query`, `folderId`, `searchType` |
| Ответ | JSON: `results[]` с `url`, `title`, `content` (выдержка из страницы), плюс опциональный `answer` | JSON-обёртка с `rawData` — base64 от XML |
| Разбор | прямой | нужен XML-парсер; документы в `groups[]` → `documents[]` |
| Готовый ответ для модели | есть: `answer` ложится в `WebSearchResult.content` | в этом эндпоинте нет; генеративный вызов отдельный |
| Сегмент | англоязычный веб в первую очередь | RU-сегмент, регионы задаются отдельно |
| Тип поиска | такого понятия нет | `searchType` (`SEARCH_TYPE_RU` / `_TR` / `_COM`) в запросе |
| Ограничение запроса | жёсткого нет | 40 слов / 400 символов |
| Онбординг | ключ из кабинета | Cloud-аккаунт, биллинг, сервисный аккаунт с ролью, каталог, API-ключ |
| Пакет в репозитории | `packages/web/web-search-tavily`, id `tavily` | отсутствует |

Отдельно про сниппет: Tavily отдаёт `content` как выдержку из целой страницы, поэтому пакет подрезает её до `maxContentChars` (по умолчанию 2000) по границе слова. У Яндекса аналог — `passages`. `publishedAt` не отдаёт ни один, но поле в seam опциональное, так что адаптеру не приходится его выдумывать.

Фактура по Яндексу взята из документации, а не из живого вызова: доки `yandex.cloud` редиректят на `aistudio.yandex.ru`, который из этой сети отдаёт captcha (проба 2026-10-07). Пакета под него нет, поэтому то, что пакет обязан обрабатывать, проверяется первым прогоном с ключом.

Ключи есть. В окружении этой сессии их нет — как и `TAVILY_API_KEY`; единственное имя в `.env` — `OPENROUTER_API_KEY`. Значит оба лежат в хранилище credentials, и это тот путь, которым провайдеры их и читают: `resolveKey` в `web-search-tavily` идёт через `ctx.get('credentials')`, а к окружению падает только без него.

### Три формы маршрутизации

| | Форма | Что даёт | Цена |
|---|---|---|---|
| A | Пин на деплой: новый пакет `web-search-yandex` с id `yandex`, `searchProvider: yandex` | в seam ничего не меняется: настройки, env и страница выбора работают как есть | один провайдер на весь деплой, переключение — правкой профиля |
| B | Пакет-роутер: регистрирует один id и раскидывает по эвристике (кириллица → Яндекс) | оба бэкенда достижимы в одном деплое | роутер владеет двумя наборами креденшлов, а скрытая цепочка приоритетов запрещена решением про volatile-конфиг: правило маршрутизации обязано быть явным полем |
| C | Правка seam'а: `provider?` в `WebSearchRequest` | выбор на уровне запроса | задевает модельный контракт и решение про web-seam, тянет схему инструмента, промпты и снапшоты |

Ещё два варианта, отвергнутых не за цену, а за смысл:

| Вариант | Почему отвергнут |
|---|---|
| Угадывать язык запроса внутри провайдера | эвристика делает источник результатов невидимым для конфигурации: по выдаче не понять, кто ответил, и обещание «выбор задаётся настройкой» перестаёт быть верным |
| Провайдер «Яндекс с фолбэком на Tavily» при ошибке | фолбэк по отказу возвращает ровно ту молчаливую подмену, от которой избавлялись: лимит или 4xx одного бэкенда незаметно менял бы выдачу |

### Открытый вопрос — решения нет

Выбор отложен сознательно: формы A, B и C описаны, ни одна не принята. Записано, чтобы следующий заход не начинал сравнение заново.

Что должно быть решено до записи решения:

- Нужна ли per-query маршрутизация вообще. Если все запросы деплоя идут в один поиск — работает A, а B и C не стоят своей цены.
- Если нужна — по какому признаку. Язык запроса, явный параметр от модели и настройка сессии — три разных решения, и в модельный контракт они попадают по-разному.
- Кто владеет двумя креденшлами, если оба бэкенда живут в одном деплое.

Чисел здесь нет намеренно: цена за 1000 запросов, задержка и доля пустых выдач на RU-запросах уходят в [MEASUREMENTS.md](MEASUREMENTS.md) после первого живого прогона. **Перемерить:** живой вызов обоих API с ключом на одном наборе RU- и EN-запросов.

## Model routing

### Как выбирается модель

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| 1 | Версия судьи | Закрепить `typesafe/jev-1.13` в конфиге, не псевдоним | Псевдоним молча переезжает на новую версию, и откалиброванные пороги перестают значить то, что значили |
| 2 | Кончился бесплатный дневной лимит | Переход на платную flash | Срабатывает по `freeMinRemaining` заранее, а после `RATE_LIMIT` на бесплатном эндпоинте — до полуночи UTC. Работа не встаёт |
| 3 | Квантизация `unknown` | Доверять только списку провайдеров (`unknownQuantization: 'trusted'`) | `unknown` объявляют и гиперскейлеры, и ноунеймы; у первых это особенность площадки, у вторых — способ не сказать. Список выведен замером |
| 4 | Нижняя граница квантизации | `fp8` на обеих ступенях | `fp4` заметно хуже именно на коде, а дешевле почти не выходит: по замеру разница 0–11.8% |
| 5 | Порог аптайма | 90%, мягкий | Если после фильтров не осталось ничего, фильтр снимается и в решение пишется `relaxedUptime: true`. От отказов защищает переключение на другого провайдера, а не отсев заранее |
| 6 | Внутри ступени строго самая дешёвая | Да, но при отказе сначала перебираются другие провайдеры **той же модели** (`preferModel`) | Иначе рейт-лимит одного провайдера молча менял бы модель посреди диалога |
| 7 | Контекст ступени flash | 1 000 000; Nemotron в составе по умолчанию нет | У `nemotron-3.5-lightning` окно 262k, и ради него пришлось бы опустить порог всей ступени |
| 8 | Сверка фактического провайдера через `/api/v1/generation` | Вне этого раунда | `only` + `allow_fallbacks: false` — жёсткое ограничение на стороне OpenRouter, проверено живым запросом. Генерации стримов появляются в API с задержкой больше минуты, поэтому сверка — отдельный фоновый сервис |
| 9 | Подбор `cacheIdleMs` по фактическим попаданиям в кэш | Фиксированные 10 минут, как окно закрепления у OpenRouter | Автоподбор по доле попаданий — следующий раунд |
| 10 | Что делать при `QUOTA`/`KEY_QUOTA` от подписочного источника | Бан сразу на `quotaCooldownMs` (дефолт 10 минут), а не после `excludeAfterFailures` подряд | Израсходованная квота — ответ, а не сбой: попытки между ними падали бы так же, тратя ход и бюджет рероутов. `RATE_LIMIT` сюда не входит — это транзиент, и он остаётся обычным рероутом |
| 11 | Где живёт переключатель OpenRouter fallback | На сессию, в чипе композера; дефолт — `fallbackToOpenRouter` (true) в профиле; выбор — событие `model-routing/openrouter-fallback` в логе сессии | Переживает рестарт хоста, как `tier-override`; сессия без выбора следует за значением профиля, пока его не изменили. Не в карточке настроек: решение о тратах принимают про разговор, а не про весь профиль |
| 12 | Что делает выключенный fallback при израсходованной квоте | Ход падает сразу с `MODEL_ROUTING_SUBSCRIPTION_LIMIT`, сообщение называет остаток кулдауна; следующее сообщение после него снова идёт на подписку | Ждать кулдаун внутри хода — значит держать сессию 10 минут. Провайдерское `providerRetryAfterMs` сюда не подходит: политика ретрая уважает это поле и удержала бы ход до конца кулдауна |
| 13 | Модель без подписочного источника при выключенном fallback | Остаётся на OpenRouter | Иначе переключатель удалял бы модели (`glm`, `space-bunny` в тире flash), а не выбирал им источник |

### `auto` включён в рабочем профиле

`agent-default-model` задавал конкретный id `stealth/space-bunny-alpha`, то есть режим `fixed`: судья не вызывался, а ранжирование шло по эндпоинтам одной модели. Главная заявленная фича — «дешевейший среди избранных автоматически» — была в рабочем профиле выключена, и ничто об этом не сообщало: `fixed` не ошибка, а допустимый режим.

Решение: в профиле `web` стоит `model: auto`. Судья выбирает ступень, внутри ступени работает ранжирование по смешанной цене. Побочный эффект, который надо держать в голове: `auto` описывает **слабейший** тир (контекст flash — 1M, но набор моделей шире), поэтому сессия без явного выбора стартует на flash и переходит на pro по решению судьи, а не сразу на pro. Кто хочет фиксированную модель — пишет её id, и это остаётся поддержанным режимом.

**2026-10-09: решение не держится само.** `agent-default-model` — не константа профиля, а строка, которую перезаписывает пикер: `saveSelection` пишет её через `configEditor` при каждом выборе модели в UI. К 18:40 там снова стоял конкретный id, на этот раз чужого маршрута (`provider: claude-proxy, model: claude-opus-5`), то есть `tiers` в обычной сессии не участвовал вовсе — решения не писались, чип был пуст. Практический вывод: `auto` — это выбор в пикере, а не состояние, закрепляемое конфигом; как значение строки соотносится с режимами — в [ROUTING.md](ROUTING.md#конфигурация).

### Границы разговора вместо решения на каждый ход

Маршрут перерешает только на `start`, `failure`, `selection-change`, `compaction` и `idle`. Причина не в экономии вызовов: смена модели или провайдера убивает prompt-кэш, а ход агента почти целиком кэшированный ввод. Между границами работает пин — `{ only: [tag], allow_fallbacks: false }` на один конкретный эндпоинт.

### Отказ провайдера внутри хода — [ADR-0002](adr/0002-reroute-pre-content-provider-failures.md), обсуждается

09.10.2026 ход умер на 400 от `morph/fp8`, хотя в тире было ещё 40 с лишним кандидатов: `INVALID_REQUEST` не входит в `rerouteCodes`, а механика рероута к тому моменту уже работала. Тот же исход дали `AUTH` (403 «Key limit exceeded») и `UNSUPPORTED_REASONING_EFFORT` — все три отказа пришли до первого контент-чанка, то есть попытка была воспроизводима. Предлагаемое решение — инвертировать политику: `rerouteCodes` (allow-list) → `noRerouteCodes` (deny-list, дефолт `CONTEXT_WINDOW_EXCEEDED`, `IMAGE_OFFLOAD_REQUIRED`, `ABORTED`). Варианты и цена — в ADR; запись здесь появится после принятия.

### Почему ранг считается по смешанной цене

Ход агента — это в основном повторное чтение уже отправленного контекста, и провайдеры, выглядящие самыми дешёвыми по цене промпта, часто не публикуют скидку на чтение кэша вовсе. Замер на `v4-pro` со 100k контекста показал перестановку мест: лидер по «цене без кэша» уходит на шестое место, как только учтён cache-read. Поэтому ключ ранжирования — `cached · cacheRead + fresh · prompt + output · completion`, а веса либо конфигурируемые по умолчанию, либо измеренные по самой сессии после `mixMinTokens`.

### Почему судья описывает слабейший тир

Судья включается, когда тиров не меньше двух: только тогда `auto` появляется в пикере. Он описывает **слабейший** тир намеренно — вызывающий, который разрешил бы `auto` против сильнейшего, получил бы окно контекста, которого нет ни у одной реально выбранной модели.

### Почему судье не передаётся вывод инструментов

В `state` судьи идёт только текст пользователя. Правдоподобный добавленный контекст переворачивает решение модели-судьи: структурированный вывод сам по себе не защищает от инъекции. Поэтому содержимое файлов и результаты инструментов судье не показываются, хотя они и были бы полезны для оценки сложности.

### Отвергнутые идеи

Таблица восстановлена из заметки `2026-10-03-model-routing-and-role-cost-policy`, удалённой вместе с триплетом: на неё не ссылался ни один активный текст, а смысл переехал в код. Записано здесь, чтобы отвергнутые варианты не выглядели свежими идеями при следующем заходе.

| Отвергнутая идея | Что вместо неё |
|---|---|
| Именованный routing-профиль, на который ссылаются маршруты | Тир — это список моделей и фильтров, без нового пространства имён |

### Цена прямого источника может быть приоритетом, а не ценой

Прямой источник с лимитным ключом (`claude-proxy`) или предоплаченной квотой (`Anthropic-token-plan-sgp`) не имеет измеримой per-token цены, и честное сравнение всегда выбирало бы OpenRouter — при том, что предоплаченная квота простаивает. Решение: ставится `usdPerToken: 1e-12` — консервативно низкое значение, которое сажает источник первым, а равные цены разрешаются порядком в `extraSources` (claude, затем Anthropic).

Это приоритет, а не цена, и диагностика показывает `1e-12` вместо реального расхода. Побочный эффект записан здесь специально: чтение `diagnosticsPath` по этим источникам не отвечает на вопрос «сколько стоил ход». Честная запись цены подписки — по-корзинная (`promptUsdPerToken` / `completionUsdPerToken` / `cacheReadUsdPerToken`), см. [model-routing-claude-proxy/STATUS.md](model-routing-claude-proxy/STATUS.md); откат на неё — однострочная правка профиля.

Отвергнутый вариант: правило «claude всегда предпочтительнее до исчерпания» как отдельная настройка. Это не цена, а правило приоритета, и его нет в коде; заводить второе понятие для того, что уже выражается ценой, — лишняя сущность.

### Почему `ctx.piAiDispatch` не идёт через `ctx.llm`

Вызывающий сам является адаптером и уже получил спроецированные сообщения. Вложенный `llm.stream()` спроецировал бы историю второй раз и срезал `replayState`, которым владеет внешний адаптер. Конфигурационный `compat.openRouterRouting` тоже не подходит: он один на маршрут, а пинить нужно на запрос.

### Коллизия терминов — решение развёрнуто

Постановка фиксировала: слово «Project» в dsh уже занято. «Project directory» — это бакет персистентности по cwd (`<configured-root>/--<normalized-cwd>--/<encoded-session-id>/session.jsonl.zstd`), без рантайм-семантики и без связи с чатами. Решение требовало, чтобы **внутренние имена пакетов и типов не содержали `project`**, а слово оставалось только пользовательским.

В коде получилось иначе: пакет `experimental/project-memory`, константа `PROJECT_PRESET_ID`, бренд `ProjectId`, поле конфигурации `projectPresets`. Разворот выглядит осознанным — читаемость кода против чистоты словаря, — но новая формулировка не записана, и опасение постановки остаётся в силе: читатель `session-persistence` будет искать в нём эту фичу. Решить одним из двух способов: либо переименовать, либо один раз развести значения в документации подсистемы.

### `.volatile()` не доходит до интерфейса: карточку нужно писать самому

Наивное ожидание от `.volatile()` — «поле появится в настройках само» — неверно, и это стоило отдельного захода. `SettingsForms.describe()` действительно проецирует volatile-поля, но мимо них лежит ещё `autoGenerate`: флаг «построй страницу из схемы». **Его не читает ни один файл в `packages/client/**`**, и сам `packages/settings/settings/README.md` говорит это прямым текстом: «for clients that build pages from the schema; no shipped client does so yet».

Практический итог: без своей карточки namespace виден по wire-API и не виден в UI вообще. Все шесть существующих страниц настроек — ручные, по одному пакету на namespace, и наш `client-ui-project-memory` продолжает этот ряд.

Что из этого следует на будущее:

- **`projectPresets` и `maxLineageDepth` намеренно оставлены не-volatile.** Первое редактирование страницы записало бы в строку профиля то, чем владеет стартовая композиция. Расколка «потолки — настройка, идентичность проекта — состав» повторена тестом `config-volatility.spec.ts`, который читает `meta.volatile` из настоящей схемы.
- **Диапазоны остаются за хостом.** Карточка отвергает только дробное значение — то, которое не пригодится ни одной границе. Верхняя и нижняя границы (`maxEntryChars` 1..100000) отвечают schemastery, и выход за них приходит отказом сохранения, а не молчаливой подрезкой в поле. Причина та же, что и в карточке model routing: хост — единственный, кто решает, какие значения осмысленны.
- **Описание инструмента про потолок не упоминает.** `memory_write` не вставляет предел в своё описание, потому что описание фиксируется при монтировании, а предел меняется вживую: значение в описании устарело бы без предупреждения. Предел называет сама ошибка отказа — `The memory text is N characters; the limit is M.` — и это единственное место, где модель его увидит.

### Что изолировано, а что нет

Изолируется **запись**, не чтение. Thread читает основной checkout свободно, и это принятое решение, а не недоделка: read-fence вне объёма первой версии. Формулировка «изолирована только запись» должна стоять в README и в UI, иначе изоляция читается сильнее, чем она есть.

До R1 (linked worktree) общедоступный object store означал, что Thread технически мог сделать `git push` — запрещалось контрактом исполнителя, а не песочницей. С R1 (D9, [plans/threads-self-contained-worktrees.md](plans/threads-self-contained-worktrees.md)) git-репозиторий Thread'а самодостаточен: общий object store исчез, `git push` в origin (путь родителя) пишет вне sandbox-root Thread'а и отклоняется **песочницей**; `git fetch` из родителя остаётся возможен, потому что пишет только в собственный `.git` клона. Запрет push'а в контракте исполнителя сохранён как вторая линия: он обязан покрывать и сессии без песочницы.

### Почему `thread/*` не добавлены в ожидаемые выходы SDK (T8.5 переформулирован)

Бэклог T8.5 требовал внести `thread/created`, `thread/status`, `thread/removed` в ожидаемые выходы TypeScript- и Python-SDK «в том же изменении», потому что `SessionEventMap` расширен. Проверка 2026-10-04 показала, что посылка неверна: файлы `snapshots/sdk/*/notifications.expected.jsonl` и `result.expected.json` — это **проекция реального прогона** записанной сессии, а не поддерживаемый руками список событий. Python-овые `eventTypes` пишет `scripts/smoke-python-runtime.py` из событий, которые прогон фактически породил. Ни один сценарий SDK не композирует бандл `threads-profile`, поэтому эти события там не появляются в принципе.

Следствие: вписать строки вручную значило бы сфабриковать вывод, которого прогон не даёт, и `DSH_SNAPSHOT=refresh` стёр бы их при первом же обновлении. Правило репозитория здесь выполняется **вакуумно**: ни одна проекция SDK этих событий не наблюдает.

Реальный пробел другой и честнее: у фичи Threads нет покрытия уровня SDK вовсе. Чтобы оно появилось, нужен новый записанный сценарий, композирующий `threads-profile` под профилем `sdk`, — то есть `test:snapshot:record` с ключом, а не правка файла. T8.5 переформулирован в «новый SDK-сценарий для Threads» и больше не блокирует upstream-PR расширением `SessionEventMap`.

## Поверхность мержа

Раздел про то, почему та или иная правка апстримного файла существует в нашем виде. Сквозной план работ — [plans/merge-surface.md](plans/merge-surface.md), замер — [INVENTORY.md](INVENTORY.md).

### `repository` — опциональная capability, а не обязательная

`SubagentCapabilities.repository` было обязательным полем, то есть **каждый** провайдер обязан был его назвать — даже чтобы сказать «не поддерживаю». На этом стояли четыре апстримных `src`-файла и восемь апстримных тестов, а также — навсегда — все будущие апстримные провайдеры: любой новый бэкенд субагентов заводил бы в нашей ветке конфликт из-за одной строки `repository: false`.

Поле сделано опциональным (`repository?: boolean`): отсутствие значения означает «не поддерживается». Поведение не изменилось — guard в `assertCapabilities` проверяет `!provider.capabilities[cap]`, а `undefined` ложен, поэтому отказ `UNSUPPORTED_CAPABILITY` на запрошенный `repository` приходит ровно как раньше. Единственное место, где тип протекал, — `tool-subagent`, где значение уходит в поле `supported`; там добавлено `?? false`.

Отвергнуто: оставить поле обязательным и продолжать писать `repository: false` (цена — конфликт в каждом новом апстримном провайдере); вводить вместо этого отдельный флаг «провайдер объявил набор» (второй способ сказать то же самое).

Замер: 181 → 166 изменённых апстримных файлов (−15).

### Почему `known-event-types.ts` остаётся нашим

Шаг «снять пять строк» из плана отменён 2026-10-10: он стоял на ложной посылке. Файл **генерируется** — `scripts/gen-persistence-catalog.ts` обходит `packages/*/*/src/**` и печатает **все** объявления `SessionEventMap` по репозиторию, а `model-routing/*` и `thread/*` объявлены нашим же кодом (`experimental/model-routing/src/types.ts`, `experimental/threads/src/types.ts`). Значит, генератор возвращает их по построению: с ними `gen-persistence-catalog` не даёт диффа, без них падает `verify-persistence-catalog` (гейт в составе `doc-sync`).

Ранбук это подтверждает: шаг 1 берёт апстримную копию, шаг 3 перегенерирует файл и возвращает строки — что и видно в истории (`2094e7ae9f`, затем `15ea3235f7`). Выигрыш в поверхности — ноль. Файл уже числился в категории «A. Перегенерируемое» [INVENTORY.md](INVENTORY.md), то есть прежняя формулировка задачи противоречила собственному инвентарю.

Фраза «события внешних плагинов отсутствуют там by construction» остаётся верной: она про плагины **вне дерева**. Наши живут в дереве, поэтому их события в списке и должны быть. Убрать эти имена из выпущенного словаря можно только сменой механизма — объявлять в `PluginRecordMap` под неймспейсом `plugin:` и писать через `appendPluginRecord()`. Это крупная переделка журнала, фолдов и снапшотов; в план сокращения поверхности не входит.

### Наши строки монтажа — в своих бандлах, а не в апстримных

Наши строки стояли в патчах апстримных бандлов: три провайдера поиска, `trustedProxyAddressRanges` и карточка настроек Threads. `packages/bundle/base/cordis.patch.yml` — самый горячий апстримный файл базы, он конфликтовал почти на каждом релизе.

Строки уехали в свои бандлы: `@deepseek-ai/dsh-web-search-profile` (новый) и `@deepseek-ai/dsh-experimental-threads-profile` (существующий). Все четыре файла `packages/bundle/base/*` и `packages/bundle/web-app/*` вернулись к апстримному виду побайтово.

Механика, на которую это опирается (`docs/user/develop/basic/publish.md`, «The loading order»): слои применяются в порядке `dsh.profile.bundles`, затем `cordis.patch.yml` профиля, затем `--patch`. Значит **свой бандл обязан идти в списке после `@deepseek-ai/dsh-base`**: его `config`-патч заменяет конфиг строки целиком, а не сливает по полям, и названный до базы слой будет перебит. Проверено контрфактом: с бандлом перед базой `searchProvider` остаётся апстримным, хотя вставки монтируются.

Композиция профиля после переезда измерена, а не выведена рассуждением: 193 строки, 0 различий до и после. В живом профиле побеждает его собственный слой — `searchProvider: tavily` (не `deepseek-official` из базы и не `duckduckgo` из нашего бандла) и пять диапазонов вместо одного, потому что `config` профиля заменяет конфиг целиком.

Неочевидное следствие, найденное при переезде и записанное отдельно: **вынос строки из бандла делает её пакет недостижимым ни для одного шипнутого профиля**, и `verify-product-use` падает с «no product runtime use». Лечится записью в `scripts/product-package-policy.ts` с категорией `optional` — так уже сделано для `subagent-thread-worktree` и `worktree-manager`. Это понадобится каждой задаче, уносящей строку из бандла.

### `dsh.catalog`: генераторы читают вклад из манифестов

`gen-tool-catalog.ts` и `gen-doc-graphs.ts` знали о наших пакетах потому, что мы дописали их в сами скрипты — включая класс-заглушку `CatalogModelRouting`, живший внутри апстримного скрипта. Это не сгенерированные артефакты, а генераторы: конфликт содержательный и растущий с каждой фичей. При этом оба списка перечисляют **пакеты**, а имя пакета известно из его манифеста.

Теперь пакет объявляет вклад у себя: `dsh.catalog` рядом с `dsh.bundle`, с под-объектами `service` (для `docs/capability-seams.md`) и `tools` (для `docs/tool-catalog.md`). Оба генератора держат свои записи литерально и вставляют объявленные. `pkg` и `dir` выводятся из имени манифеста и его каталога, а не переписываются, и расхождение с манифестом — ошибка. Порядок не выводится ни из какого естественного ключа (оба списка не отсортированы), поэтому у каждой записи есть якорь `after`, называющий запись, за которой она встаёт; неоднозначность якоря проверяется до вставки, иначе проход мог бы молча поставить запись не туда.

Строительные леса монтирования уехали из скрипта в пакеты: `@deepseek-ai/dsh-experimental-model-routing/catalog` и подпути `./catalog` у `tool-threads` и `project-memory`, экспортирующие `mount(ctx)`. Генератор импортирует спецификатор из манифеста и не называет ни класса, ни пакета.

Единственное исключение — роль `piAiDispatch`: она осталась **литеральной строкой** в `gen-doc-graphs.ts`, потому что владеет ею апстримный пакет `llm-pi-ai`, а его манифест не должен становиться нашим файлом ради одной строки (см. раздел про `piAiDispatch` выше). Это осознанное послабление к правилу «в остатке нет имён наших пакетов». Проверка результата: остаток диффа `gen-tool-catalog.ts` не называет ни одного нашего пакета вовсе, а все девять сгенерированных документов совпали по хешам до и после переделки.

### `scripts/no-unknown-casts.baseline.json` — тоже генерируемое

Гейт `verify-no-unknown-casts` запрещает новые приведения к `unknown` и сверяет дерево с файлом-инвентарём. Инвентарь апстримный, и в шаге 1 ранбука он берётся из апстрима.

Две подробности, которые делают его генерируемым, а не ручным:

- Гейт проверяет **сначала добавленные** приведения и только потом устаревшие записи. Пока в дереве были свои 17 приведений, гейт падал на них и до устаревших не доходил.
- Сняв свои 17, мы получили красный гейт уже на **двух устаревших записях**, которые форк унаследовал: `packages/client/ui-chat` (апстримная запись снята, потому что наша правка `restoreAt` изменила литерал) и `packages/core/session/src/index.ts` (двойное приведение заменено на обычное). Обе записи предшествуют нашей работе, и восстановить их можно только вернув снятые приведения.

Поэтому `--prune` добавлен в шаг 3 ранбука: шаг 1 берёт апстримный инвентарь, шаг 3 приводит его к нашему дереву. Порядок обязателен — `--prune` гоняется **после** того, как сняты все свои приведения, иначе гейт упадёт на добавленных.

Практическая цена честно: `--prune` переписывает файл целиком в своём порядке сортировки, поэтому дифф на 2 удалённые записи выглядит как ~50 строк. Сам гейт остаётся чувствительным к новым приведениям — а это единственное, ради чего он нужен.

### `client/ui-workspace`: форк презентации, но шов данных чистый

Разобрано 2026-10-10. Проверены все 92 клиентских слота: слота для **дочерних строк под строкой сессии** нет. Ближайшее — `sidebar.session.row.leading` и `.hover` (декорации внутри строки), `sidebar.workspaces.session.menu.item` и `.row.action` (меню и кнопки строки). Ни один не даёт добавить строку в дерево.

Поэтому вложение Thread'ов под строку Project — форк `ui-workspace` (8 файлов), а не регистрация. Механизм «занять ключ и заменить рендерер», принятый в этом репозитории для `conversation.chat.node`, здесь недоступен: `sidebar.workspaces` — слот `single`, занятый `WorkspaceBrowser`, так что «свой рендерер» означал бы переписывание всей области браузера.

Что скрашивает решение: **шов данных чистый**. Строки Thread'ов читаются из опубликованной проекции `threads` через обычную пер-ключевую механику и переузконяются локальным типом; пакет намеренно не зависит от пакета Threads. То есть изменение изолировано в презентации, ядро не тронуто, лишняя зависимость не протащена.

Решение: **принять форк**, записав причину. Вернуться к вопросу стоит, если апстрим заведёт слот дочерних строк — тогда все 8 файлов уезжают в наш клиентский пакет.

### `client/ui-chat`: свой рендерер строки пользовательского сообщения

Фича «Restore» форкает сессию префиксом до сообщения и возвращает текст в композер. Правка протянула проп `restoreAt` через всю цепочку рендера — 15 апстримных файлов.

Разобрано 2026-10-10: слот `conversation.chat.node` — `kind: 'keyed'`, ключ = `ChatNodeKind`, и **переиспользование занятого ключа заменяет рендерер**. Строка пользовательского сообщения — это ключ `user`. При этом `forkAt` уже есть в апстримном `ChatNodeOwnerProps`; нашим был только `restoreAt`.

Значит новый слот просить не нужно — нужно зарегистрировать свой рендерер на существующий ключ из своего пакета. Апстримный дифф становится нулевым, а плата — владение презентацией строки: вложения, ссылки на файлы, редактирование, скиллы придётся догонять. В каталоге слотов это помечено `shadows-shipped-ui`.

Решение: идти этим путём, но только после проверки в живом приложении, что копия строки не теряет ни одной апстримной возможности. Если теряет — честнее оставить правку и записать, что `ui-chat` мы форкаем.

## Критерии готовности

Плагин готов не тогда, когда зелёные тесты, а когда выполнены все пять:

1. Сценарий «Project → два Thread'а → оба завершились → координатор видит ветки и диффы → сливает → архивирует» проходит и в записанном снапшоте сессии, и в real-API e2e.
2. Установка в чистый `DSH_HOME` из `.tgz` или npm: `dsh plugin --profile web add <пакет>`, перезапуск, ни одной записи «did not activate».
3. Обычные, не-Project сессии в профиле с бандлом ведут себя ровно как без него: тот же набор инструментов, тот же провайдер субагентов.
4. После удаления бандла Project-сессии открываются (события плагина помечены `ignorable`), worktree остаются на диске, README говорит, как их убрать.
5. Все гейты репозитория, которые касаются изменённых файлов, зелёные.

Пункты 3 и 4 — это то, что отличает «работает у меня» от «можно отдать»: первый проверяет, что плагин не протёк в чужие сессии, второй — что его можно снять без порчи данных.
