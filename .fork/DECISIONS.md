# Принятые решения

Почему плагины устроены так, а не иначе. Здесь только то, что **не выводится из кода**: код говорит, что происходит, а этот файл — почему выбран именно такой вариант и что было отвергнуто.

Решения перенесены сюда 2026-10-04 из рабочих документов двух сессий разработки, которые лежат вне репозитория (`default-workspace`, см. [README.md](README.md#где-исходные-документы)). До переноса на них ссылались комментарии в коде вида `§19 №1`, `§B.1`, `C8` — эти ссылки уезжали в `lib/types/*.d.ts` и в публичные README, указывая на документ, которого читатель не видит. Заменять их надо на ссылки сюда.

Числа, на которых стоят решения, — в [MEASUREMENTS.md](MEASUREMENTS.md).

## Web fetch

### Доступ к локальным адресам — объявленный диапазон, а не флаг

Задача — fetch до сервиса на этой машине или в LAN (локальный dev-сервер, NAS, страница админки роутера). Штатный guard отвергает любой непубличный адрес, и это правильно: он существует, чтобы ответ DNS не увёл запрос к `127.0.0.1` или в RFC1918.

| Вариант | Почему отвергнут |
|---|---|
| Логический флаг `allowLocal: true` | Открывает разом loopback, RFC1918, link-local и CGNAT — то есть всю поверхность, ради которой guard и стоит. Не отличить dev-сервер от чужого сервиса на том же хосте |
| Белый список хостов (`localhost`, имена) | Имя разрешается через DNS в момент запроса; guard проверяет адрес, а имя можно переопределить в hosts. Проверка имени — не проверка адреса |
| **Объявленный CIDR-диапазон** (принято) | Оператор называет ровно те блоки, которые считает своими. Всё вне их остаётся закрытым: объявление loopback не открывает RFC1918, и это покрыто тестом |

Разворот сделан в апстримном пакете `packages/web/web-fetch-http` (`trustedProxyAddressRanges`, компиляция CIDR в `network.ts`, применение в provider), потому что расширить guard извне нельзя — адрес проверяется внутри самой функции запроса. Это категория B инвентаря: точка входа конфигурации, а не обход.

Практическая цена: объявленный блок перестаёт быть барьером для **своего** диапазона. Запись в профиле — по строке на диапазон в `web-fetch-http`, каждая со своим комментарием; удаление строки возвращает guard для диапазона. Имя `trustedProxyAddressRanges`, а не `allowLocal`, стоит по той же причине, по которой решение отвергло флаг: значение — это блоки, а не разрешение.

Список должен быть **полным для этой машины**. Когда transparent-proxy работает в режиме fake-ip/TUN, системный DNS отвечает на каждый домен синтетическим адресом из пула `198.18.0.0/15` (замер 2026-10-05: `dns.lookup('claude.com')` → `198.18.2.112`), и без этого блока падает fetch до любого сайта. Итог для этой машины: LAN-диапазоны `127.0.0.0/8`, `::1/128`, `192.168.0.0/16`, `10.0.0.0/8` плюс fake-ip пул `198.18.0.0/15`.

Строка `config:` в патче профиля **заменяет весь config строки бандла целиком**, глубокого слияния нет — это уже записано комментарием в самом `~/.dsh/profiles/web/cordis.patch.yml` применительно к `threads-preset`. Поэтому частичное перечисление молча удаляет диапазоны бандла: `packages/bundle/base/cordis.patch.yml` несёт дефолт `web-fetch-http.trustedProxyAddressRanges: [198.18.0.0/15]`, а живой профиль перечисляет свою строку `web-fetch-http` только с LAN-диапазонами и тем самым теряет `198.18.0.0/15`. Живые пробы 2026-10-05: `web_fetch http://127.0.0.1:48777/` прошёл, `web_fetch https://claude.com/blog/projects-redesigned` упал с ошибкой про non-public IP — LAN-диапазоны профиля активны, а fake-ip пул в живом конфиге отсутствует.

Исправление, применённое вне репозитория: в список `trustedProxyAddressRanges` строки `web-fetch-http` в `~/.dsh/profiles/web/cordis.patch.yml` добавлен `198.18.0.0/15`; после правки `web_fetch` до `claude.com` проходит (HTTP 200).

## Model routing

### Как выбирается модель

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| 1 | Версия судьи | Закрепить `typesafe/jev-1.13` в конфиге, не псевдоним | Псевдоним молча переезжает на новую версию, и откалиброванные пороги перестают значить то, что значили |
| 2 | Кончился бесплатный дневной лимит | Переход на платную flash | Срабатывает по `freeMinRemaining` заранее, а после `RATE_LIMIT` на бесплатном эндпоинте — до полуночи UTC. Работа не встаёт |
| 3 | Квантизация `unknown` | Доверять только списку провайдеров (`unknownQuantization: 'trusted'`) | `unknown` объявляют и гиперскейлеры, и ноунеймы; у первых это особенность площадки, у вторых — способ не сказать. Список выведен замером |
| 4 | Нижняя граница квантизации | `fp8` на обеих ступенях | `fp4` заметно хуже именно на коде, а дешевле почти не выходит: по замеру разница 0–11.8% |
| 5 | Порог аптайма | 90%, мягкий | Если после фильтров не осталось ничего, фильтр снимается и в решение пишется `relaxedUptime: true`. От отказов защищает переключение на другого провайдера, а не отсев заранее |
| 6 | Внутри ступени строго самая дешёвая | Да, но при отказе сначала перебираются другие провайдеры **той же модели** (`preferModel`) | Иначе рейт-лимит одного провайдера молча менял бы модель посреди диалога |
| 7 | Контекст ступени flash | 1 000 000; Nemotron в составе по умолчанию нет | У `nemotron-3.5-lightning` окно 262k, и ради него пришлось бы опустить порог всей ступени |
| 8 | Сверка фактического провайдера через `/api/v1/generation` | Вне этого раунда | `only` + `allow_fallbacks: false` — жёсткое ограничение на стороне OpenRouter, проверено живым запросом. Генерации стримов появляются в API с задержкой больше минуты, поэтому сверка — отдельный фоновый сервис |
| 9 | Подбор `cacheIdleMs` по фактическим попаданиям в кэш | Фиксированные 10 минут, как окно закрепления у OpenRouter | Автоподбор по доле попаданий — следующий раунд |

### `auto` включён в рабочем профиле

`agent-default-model` задавал конкретный id `stealth/space-bunny-alpha`, то есть режим `fixed`: судья не вызывался, а ранжирование шло по эндпоинтам одной модели. Главная заявленная фича — «дешевейший среди избранных автоматически» — была в рабочем профиле выключена, и ничто об этом не сообщало: `fixed` не ошибка, а допустимый режим.

Решение: в профиле `web` стоит `model: auto`. Судья выбирает ступень, внутри ступени работает ранжирование по смешанной цене. Побочный эффект, который надо держать в голове: `auto` описывает **слабейший** тир (контекст flash — 1M, но набор моделей шире), поэтому сессия без явного выбора стартует на flash и переходит на pro по решению судьи, а не сразу на pro. Кто хочет фиксированную модель — пишет её id, и это остаётся поддержанным режимом.

### Границы разговора вместо решения на каждый ход

Маршрут перерешает только на `start`, `failure`, `selection-change`, `compaction` и `idle`. Причина не в экономии вызовов: смена модели или провайдера убивает prompt-кэш, а ход агента почти целиком кэшированный ввод. Между границами работает пин — `{ only: [tag], allow_fallbacks: false }` на один конкретный эндпоинт.

### Почему ранг считается по смешанной цене

Ход агента — это в основном повторное чтение уже отправленного контекста, и провайдеры, выглядящие самыми дешёвыми по цене промпта, часто не публикуют скидку на чтение кэша вовсе. Замер на `v4-pro` со 100k контекста показал перестановку мест: лидер по «цене без кэша» уходит на шестое место, как только учтён cache-read. Поэтому ключ ранжирования — `cached · cacheRead + fresh · prompt + output · completion`, а веса либо конфигурируемые по умолчанию, либо измеренные по самой сессии после `mixMinTokens`.

### Почему судья описывает слабейший тир

Судья включается, когда тиров не меньше двух: только тогда `auto` появляется в пикере. Он описывает **слабейший** тир намеренно — вызывающий, который разрешил бы `auto` против сильнейшего, получил бы окно контекста, которого нет ни у одной реально выбранной модели.

### Почему судье не передаётся вывод инструментов

В `state` судьи идёт только текст пользователя. Правдоподобный добавленный контекст переворачивает решение модели-судьи: структурированный вывод сам по себе не защищает от инъекции. Поэтому содержимое файлов и результаты инструментов судье не показываются, хотя они и были бы полезны для оценки сложности.

### Отвергнутые идеи

Таблица восстановлена из заметки `2026-10-03-model-routing-and-role-cost-policy`, удалённой вместе с триплетом: на неё не ссылался ни один активный текст, а смысл переехал в код. Записано здесь, чтобы отвергнутые варианты не выглядели свежими идеями при следующем заходе.

| Отвергнутая идея | Что вместо неё |
|---|---|
| Именованный routing-профиль, на который ссылаются маршруты | Тир — это список моделей и фильтров, без нового пространства имён |
| Первый класс `role`, который несёт модель | `role` без модели — тот же именованный профиль под другим именем; `tierContract` в `threads-preset` добавляет координатору выбор, но не вводит новый словарь сущностей |
| Самая дешёвая точка как база скидки | База — смешанная цена хода с поправкой на кэш |
| Живая загрузка цен внутри `packages/llm/llm-pi-ai` | Выбор делает `model-routing` выше `llm` по слоям; `llm-pi-ai` получает только `ctx.piAiDispatch`, то есть блок, а не политику |
| Отдельный плагин, публикующий цены для других | Это разворот зависимостей: читатель решает сам и держит свой кэш (`EndpointsCache`) |
| Дешёвый исполнитель не проверяет план | Координатору сказано отдавать проектировочные решения на pro, а `thread_tier` переключает уже работающий Thread |

### Почему `ctx.piAiDispatch` не идёт через `ctx.llm`

Вызывающий сам является адаптером и уже получил спроецированные сообщения. Вложенный `llm.stream()` спроецировал бы историю второй раз и срезал `replayState`, которым владеет внешний адаптер. Конфигурационный `compat.openRouterRouting` тоже не подходит: он один на маршрут, а пинить нужно на запрос.

### Исход для `ctx.piAiDispatch`: апстрим, а не вендоринг

Развилка из [plans/model-routing.md](plans/model-routing.md), закрыта 2026-10-04.

| Вариант | Оценка |
|---|---|
| **Отправить `dispatch.ts` в апстрим отдельным PR** (принято) | Файл самодостаточен: один сервис `ctx.piAiDispatch`, один тип блока, ноль изменений в существующем поведении маршрутов. После мержа плагин чистый, версии связываются обычным `peerDependencies`, а новый файл в апстриме — это ровно та поверхность конфликтов, которой форк и добивается |
| Вендорить путь диспетчеризации, импортировав `@earendil-works/pi-ai` напрямую | Пришлось бы переписать у себя разрешение креденшелов, снимок конфигурации, idle-watchdog и teardown — то есть форк живого пути запроса `llm-pi-ai`, который придётся синхронизировать с ядром руками. Для форка, чья цель — скучный мерж, это движение в обратную сторону |

Решающий довод: вендоринг копирует **поведение ядра**, апстрим-файл его только **добавляет**. Если PR застрянет в ревью дольше, чем терпимо, решение можно развернуть на вендоринг, но первой попыткой должен быть апстрим — иначе форк заводит себе ручную синхронизацию там, где её можно не заводить вовсе.

### Коллизия терминов — решение развёрнуто

Постановка фиксировала: слово «Project» в dsh уже занято. «Project directory» — это бакет персистентности по cwd (`<configured-root>/--<normalized-cwd>--/<encoded-session-id>/session.jsonl.zstd`), без рантайм-семантики и без связи с чатами. Решение требовало, чтобы **внутренние имена пакетов и типов не содержали `project`**, а слово оставалось только пользовательским.

В коде получилось иначе: пакет `experimental/project-memory`, константа `PROJECT_PRESET_ID`, бренд `ProjectId`, поле конфигурации `projectPresets`. Разворот выглядит осознанным — читаемость кода против чистоты словаря, — но новая формулировка не записана, и опасение постановки остаётся в силе: читатель `session-persistence` будет искать в нём эту фичу. Решить одним из двух способов: либо переименовать, либо один раз развести значения в документации подсистемы.

### `.volatile()` не доходит до интерфейса: карточку нужно писать самому

Наивное ожидание от `.volatile()` — «поле появится в настройках само» — неверно, и это стоило отдельного захода. `SettingsForms.describe()` действительно проецирует volatile-поля, но мимо них лежит ещё `autoGenerate`: флаг «построй страницу из схемы». **Его не читает ни один файл в `packages/client/**`**, и сам `packages/settings/settings/README.md` говорит это прямым текстом: «for clients that build pages from the schema; no shipped client does so yet».

Практический итог: без своей карточки namespace виден по wire-API и не виден в UI вообще. Все шесть существующих страниц настроек — ручные, по одному пакету на namespace, и наш `client-ui-project-memory` продолжает этот ряд.

Что из этого следует на будущее:

- **`projectPresets` и `maxLineageDepth` намеренно оставлены не-volatile.** Первое редактирование страницы записало бы в строку профиля то, чем владеет стартовая композиция. Расколка «потолки — настройка, идентичность проекта — состав» повторена тестом `config-volatility.spec.ts`, который читает `meta.volatile` из настоящей схемы.
- **Диапазоны остаются за хостом.** Карточка отвергает только дробное значение — то, которое не пригодится ни одной границе. Верхняя и нижняя границы (`maxEntryChars` 1..100000) отвечают schemastery, и выход за них приходит отказом сохранения, а не молчаливой подрезкой в поле. Причина та же, что и в карточке model routing: хост — единственный, кто решает, какие значения осмысленны.
- **Описание инструмента про потолок не упоминает.** `memory_write` не вставляет предел в своё описание, потому что описание фиксируется при монтировании, а предел меняется вживую: значение в описании устарело бы без предупреждения. Предел называет сама ошибка отказа — `The memory text is N characters; the limit is M.` — и это единственное место, где модель его увидит.

### Что изолировано, а что нет

Изолируется **запись и git-состояние**, не чтение. Thread читает основной checkout свободно, и это принятое решение, а не недоделка: read-fence вне объёма первой версии. Общий object store означает, что Thread технически может сделать `git push` — это запрещено контрактом исполнителя, а не песочницей. Формулировка «изолирована только запись» должна стоять в README и в UI, иначе изоляция читается сильнее, чем она есть.

### Почему `thread/*` не добавлены в ожидаемые выходы SDK (T8.5 переформулирован)

Бэклог T8.5 требовал внести `thread/created`, `thread/status`, `thread/removed` в ожидаемые выходы TypeScript- и Python-SDK «в том же изменении», потому что `SessionEventMap` расширен. Проверка 2026-10-04 показала, что посылка неверна: файлы `snapshots/sdk/*/notifications.expected.jsonl` и `result.expected.json` — это **проекция реального прогона** записанной сессии, а не поддерживаемый руками список событий. Python-овые `eventTypes` пишет `scripts/smoke-python-runtime.py` из событий, которые прогон фактически породил. Ни один сценарий SDK не композирует бандл `threads-profile`, поэтому эти события там не появляются в принципе.

Следствие: вписать строки вручную значило бы сфабриковать вывод, которого прогон не даёт, и `DSH_SNAPSHOT=refresh` стёр бы их при первом же обновлении. Правило репозитория здесь выполняется **вакуумно**: ни одна проекция SDK этих событий не наблюдает.

Реальный пробел другой и честнее: у фичи Threads нет покрытия уровня SDK вовсе. Чтобы оно появилось, нужен новый записанный сценарий, композирующий `threads-profile` под профилем `sdk`, — то есть `test:snapshot:record` с ключом, а не правка файла. T8.5 переформулирован в «новый SDK-сценарий для Threads» и больше не блокирует upstream-PR расширением `SessionEventMap`.

### Открытые вопросы, на которые ответа ещё нет

- Нужен ли режим без изоляции как осознанный fallback. Project может работать в не-git каталоге — тогда Thread'ы недоступны вовсе. Это уже наблюдалось: сессия, запущенная из каталога вне репозитория, получала `worktree-manager: not a git work tree`, и ни один Thread не стартовал. Провайдер берёт `repoRoot` из cwd родителя, и настроить это нельзя.
- Показывать ли путь worktree модели координатора. Сейчас виден: полезно для ручного слияния, но это деталь реализации в модельном контексте.
- Расположение worktree: `~/.dsh/worktrees` или рядом с проектом.

## Критерии готовности

Плагин готов не тогда, когда зелёные тесты, а когда выполнены все пять:

1. Сценарий «Project → два Thread'а → оба завершились → координатор видит ветки и диффы → сливает → архивирует» проходит и в записанном снапшоте сессии, и в real-API e2e.
2. Установка в чистый `DSH_HOME` из `.tgz` или npm: `dsh plugin --profile web add <пакет>`, перезапуск, ни одной записи «did not activate».
3. Обычные, не-Project сессии в профиле с бандлом ведут себя ровно как без него: тот же набор инструментов, тот же провайдер субагентов.
4. После удаления бандла Project-сессии открываются (события плагина помечены `ignorable`), worktree остаются на диске, README говорит, как их убрать.
5. Все гейты репозитория, которые касаются изменённых файлов, зелёные.

Пункты 3 и 4 — это то, что отличает «работает у меня» от «можно отдать»: первый проверяет, что плагин не протёк в чужие сессии, второй — что его можно снять без порчи данных.
