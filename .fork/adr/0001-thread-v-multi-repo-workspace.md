# ADR-0001: Thread выбирает репозиторий внутри каталога Project'а

- Статус: accepted
- Дата: 2026-10-07

Закрывает открытый вопрос «Нужен ли режим без изоляции как осознанный fallback» из [DECISIONS.md](../DECISIONS.md) — тот, где Project в не-git каталоге оставляет Thread'ы недоступными вовсе.

## Контекст

Project — обычная сессия с пресетом `project`, и её рабочий каталог не обязан быть репозиторием. Наблюдаемый случай: Project запущен из `/Users/user/dev/assistant`, где лежат три независимых репозитория (`bro_bot_browser`, `tg_assistant`, `tg_bro_bot`), а сам каталог репозиторием не является. В такой сессии не стартует ни один Thread: провайдер `subagent-thread-worktree` берёт `repoRoot` из `parent.session.header.cwd`, а `WorktreeService.requireRepoTopLevel` прогоняет `git rev-parse --is-inside-work-tree` и отказывает `NOT_A_GIT_REPO` с текстом `worktree-manager: not a git work tree: /Users/user/dev/assistant`. Воспроизведено в сессии `3cde6608` и в отчёте того же захода.

Дальше по пути та же посылка зашита второй раз: `childCwd` отображает cwd Project'а в worktree как `relative(parentTop, parentCwd)`, то есть работает только когда cwd Project'а лежит **внутри** выбранного репозитория. Каталог-объединение этому не удовлетворяет ни при каком выборе репозитория.

Три свойства уже устроены правильно и определили выбор:

1. Сервис пер-репозиторный. Каталог worktree — `sha256(repoRoot)`, потолок `maxWorktreesPerRepo` считается по `repoRoot`, а `repoRoot` хранится в записи реестра. Один репозиторий на Thread — это уже действующая модель сервиса, а не новое ограничение.
2. `WorktreeSpec.repoRoot` документирован как «любой путь внутри checkout'а»: сервис умеет принимать репозиторий, отличный от cwd вызывающего.
3. `repoRootResolution: 'parent-cwd'` эту задачу не решает: пустой `repoRoot` разрешается в checkout, из которого запущен harness, а не в каталог сессии, и провайдер всё равно передаёт cwd явно.

Цена решения — правка шва подагентов: `ContinuableCreateRequest` несёт только `sessionId`, `parent` и `signal`, поэтому выбор репозитория, сделанный моделью, физически некуда положить до расширения этого типа. Это категория C инвентаря, и та же подсистема уже правится локально.

## Решение

**Репозиторий называет Thread, а не cwd Project'а.**

1. У инструмента `subagent` появляется необязательный параметр `repository` — путь внутри каталога Project'а, называющий репозиторий (обычно имя подкаталога). Координатор обязан его называть, когда Project содержит больше одного репозитория.
2. Значение доходит до провайдера: `request` в `ContinuableStartSpec` → `ContinuableCreateRequest` → `prepareContinuable`. Тип запроса расширяется полем провайдер-специфичных опций; это правка апстримного шва, а не обход через переменную окружения.
3. Провайдер передаёт в `worktrees.create` выбранный репозиторий как `repoRoot`. Сегодня там стоит `parent.session.header.cwd`, и именно эта строка делает фичу неприменимой в каталоге-объединении.
4. cwd Thread'а — корень worktree выбранного репозитория. Отображение `relative(parentTop, parentCwd)` для этого случая не применяется: cwd Project'а лежит вне репозитория, и путь начинался бы с `..`. Если координатор назвал подкаталог **внутри** репозитория, отображение сохраняется, но считается от корня репозитория, а не от каталога Project'а.
5. Репозиторий разрешается существующим `resolveRepoTopLevel`. Несуществующий путь, файл или каталог вне work tree — отказ `NOT_A_GIT_REPO`, в тексте которого перечислены найденные репозитории: координатор должен узнать, из чего выбирать, а не перебирать имена.
6. Выбор не нужно повторять при холодном resume: `repoRoot` уже durable в записи реестра, cwd ребёнка — в заголовке сессии. `prepareContinuable` вызывается только на первой активации.

Текст контракта координатора меняется вместе с кодом: сейчас слияние описано как `git fetch` плюс `git merge` «в Project checkout», и при нескольких репозиториях это надо назвать checkout'ом выбранного репозитория.

## Рассмотренные варианты

- **Автопоиск единственного вложенного репозитория** — работает ровно до второго репозитория, после чего поведение меняется от добавления каталога, которого координатор не создавал. Тихая догадка о намерении там, где цена ошибки — Thread, пишущий не в тот репозиторий. Отвергнут.
- **Режим без изоляции как fallback** — снимает симптом и ломает свойство, ради которого фича существует: параллельные Threads писали бы в один рабочий каталог, а `git push` внутри каталога Project'а был бы разрешён песочницей. Отвергнут; формулировка «изолирована только запись» не даёт права убирать изоляцию записи целиком.
- **Сделать корень workspace репозиторием с субмодулями** — переносит задачу на пользователя: три существующих репозитория требуют конвертации, а каталог-объединение перестаёт быть тем, чем его сделали. Отвергнут.
- **Список репозиториев в конфигурации деплоя** — дёшево по правкам, но Project теряет возможность работать с двумя репозиториями в одной сессии, и выбор, который обязана делать модель, всё равно остаётся невыраженным. Отвергнут в пользу параметра инструмента.
- **Один worktree на несколько репозиториев** — запись, ветка и потолок сервиса ключуются по `repoRoot`, и `thread_diff` читает один репозиторий. Решение потребовало бы новой сущности в сервисе ради сценария, которого пока никто не просил. Отвергнут.

## Последствия

**Хорошо.** Фича работает в каталоге-объединении, то есть в том виде workspace, ради которого Project и существует. Изоляция сохраняется полностью: Thread по-прежнему получает самодостаточный клон и не может писать в родителя. Появляется возможность, которой раньше не было по построению: параллельные Threads в **разных** репозиториях одного Project'а не пересекаются ни файлами, ни ветками.

**Плохо.** Требуются правки двух апстримных пакетов — схемы инструмента и типа запроса, — и вторая из них задевает durable дескриптор подагента. Модельный контракт становится на один параметр длиннее. Ошибка в имени репозитория обнаруживается только при старте Thread'а.

**Нейтрально.** Связь «cwd Project'а → cwd Thread'а» перестаёт быть вложенностью: cwd Project'а остаётся каталогом-объединением, а cwd Thread'а — корнем репозитория. Для Project'а, чей cwd сам является репозиторием, поведение не меняется: единственный репозиторий можно не называть.

## Что не входит в решение

- Thread, видящий несколько репозиториев сразу. Один Thread — один репозиторий.
- Read-fence: чтение за пределами worktree по-прежнему разрешено, как и для однорепозиторного случая.
- Послабления песочницы. Самодостаточный клон остаётся единственным способом уложиться в один sandbox-root.
- Диалог «New Project» (приоритет 9 в [STATUS.md](../STATUS.md)). Выбор репозитория при создании Project'а и выбор репозитория на каждый Thread — разные вопросы, и этот ADR отвечает только на второй.

## Как проверить

- Фикстура-каталог с двумя вложенными репозиториями: Thread стартует при названном репозитории, а worktree создаётся из него, а не из каталога-объединения.
- Отказ при неназванном репозитории в Project'е с несколькими: текст содержит список найденных репозиториев.
- Project, чей cwd сам является репозиторием: поведение прежнее, параметр не нужен.
- Холодный resume Thread'а в выбранном репозитории: cwd и `repoRoot` восстанавливаются, `prepareContinuable` повторно не вызывается.
- Параллельные Threads в двух разных репозиториях одного Project'а: ветки и рабочие каталоги не пересекаются.

## Когда пересматривать

Если у Thread'а появится законная нужда видеть два репозитория одновременно — тогда нужна сущность уровня сервиса, а не второй параметр. И если в апстриме появится штатный канал провайдер-специфичных опций делегирования, пункт 2 решения заменяется на него: наша правка типа запроса существует только потому, что такого канала нет.
